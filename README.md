# 契约驱动式 AI 开发

> 一套面向程序员的工程化 AI 辅助开发方法论。通过「产品契约、技术契约、测试契约」三类交付契约，将模糊的自然语言需求转化为明确、可执行、可验证的工程约束，使 AI 在可控的流程中完成开发任务，实现从「模糊尝试」到「可控交付」的转变。

## 核心理念

AI 辅助开发不应该只是让 AI 根据自然语言描述直接编写代码。有工程经验的程序员，应该将自身的技术理解、工程经验转化为明确的开发规范、交付契约和质量验收标准，让 AI 在可控的工程流程中完成开发任务。

契约驱动式 AI 开发的核心是：**在正式编码前，由开发者与 AI 共同制定交付契约，明确业务目标、技术实现方案及质量验收标准，并以此作为整个开发过程的统一依据。**

本方法论主要面向前后端协同的 Web 应用开发场景，但核心思想可适配至其他软件开发领域。

---

## 为什么需要契约驱动

直接使用自然语言描述需求、让 AI 编写代码、再根据运行结果反复修改，会引发一系列问题：

| 问题 | 说明 |
|------|------|
| **需求理解歧义** | AI 对自然语言的理解存在天然歧义，缺少「完成」的统一定义，反复修改中需求不断漂移 |
| **隐含约束遗漏** | AI 难以识别开发者未明确描述的隐含约束，代码能运行不代表业务需求已完整满足 |
| **自写自测盲区** | AI 自行编写、修改代码时，难以跳出自身假设，缺少独立的代码审查机制 |
| **架构一致性下降** | AI 倾向追求局部最优，易出现跨层调用、重复实现、引入不一致依赖等问题 |
| **隐性回归风险** | 为修复当前问题而破坏其他模块，缺少系统性的变更影响分析 |
| **任务顺序混乱** | 复杂需求缺少明确的任务拆解与依赖管理，前置任务未完成便开展后续开发 |
| **需求蔓延** | 实现 A 功能时顺带修改 B 和 C，变更范围超出预期 |
| **代码黑盒化** | 代码能运行但开发者不理解，逐渐沦为被动验收代码的质检员 |

**契约驱动将模糊的自然语言需求转化为明确、可执行、可验证的工程约束**，从需求理解、技术实现到质量验收全程有据可依，从根本上减少上述风险。

## 三类交付契约

本方法论定义三类交付契约，相互配合构成完整的交付契约体系：

| 契约类型 | 说明 | 编写时机 |
|----------|------|----------|
| **产品契约** | 明确业务目标、业务规则、业务流程、需求范围及边界 | 需求分析阶段，前后端共用 |
| **技术契约** | 明确技术实现方案、架构约束、模块职责及具体实现要求 | 后端/前端独立交付前，分别编写 |
| **测试契约** | 明确测试范围、测试策略、测试用例及预期结果 | 技术契约定稿后，分别编写 |

**原则**：产品契约是前后端共同遵循的业务基准；技术契约和测试契约由前后端分别编写，各自独立，分别约束对应的技术实现与质量验证。

## 需求等级划分

根据需求规模、影响范围、业务风险及技术复杂度，将需求划分为三个等级：

| 等级 | 定义 | 契约要求 |
|------|------|----------|
| **L1 — 简单需求** | 修改范围小、逻辑明确、不涉及复杂数据结构或架构变更、风险低 | 编写轻量级交付契约，不强制要求完整的三份契约 |
| **L2 — 普通需求** | 涉及多个模块、存在技术设计与业务规则、需要较完整的测试与验收 | 编写完整的产品契约、技术契约、测试契约 |
| **L3 — 复杂需求** | 涉及核心业务流程或多个子系统、重大架构调整、风险高、范围大 | 拆分为多个可独立交付的阶段，每阶段独立完成三份契约 |

## 整体交付流程

标准交付流程分为以下阶段：

```
┌─────────────────────────────────────────────────────────────────────────┐
│                        项目上下文初始化                                   │
│  （新项目：建立技术基线 | 存量项目：AI 分析代码，梳理项目上下文）            │
└─────────────────────────────────────────────────────────────────────────┘
                                    ↓
┌─────────────────────────────────────────────────────────────────────────┐
│                        需求分析与产品契约制定                             │
│  （需求沟通 → AI 反问补全 → 需求等级判定 → 生成产品契约 → 开发者审核定稿）  │
└─────────────────────────────────────────────────────────────────────────┘
                                    ↓
┌─────────────────────────────┐     ┌─────────────────────────────┐
│      后端独立交付阶段        │     │      前端独立交付阶段        │
│  ┌─────────────────────┐    │     │  （等待后端独立交付完成后启动）│
│  │ 1. 后端技术契约编写  │    │     │                             │
│  │ 2. 后端测试契约编写  │    │     │  1. 前端技术契约编写         │
│  │ 3. 三份契约独立审查  │    │     │  2. 前端测试契约编写         │
│  │ 4. 后端代码开发      │    │     │  3. 三份契约独立审查         │
│  │ 5. 接口自动化测试    │    │     │  4. 前端代码开发             │
│  │ 6. 交付成果独立审查  │    │     │  5. 页面自动化测试           │
│  └─────────────────────┘    │     │  6. 交付成果独立审查         │
└─────────────────────────────┘     └─────────────────────────────┘
                                    ↓
┌─────────────────────────────────────────────────────────────────────────┐
│                          整体验收与交付                                   │
│  （人工联调验收 → 问题归属与修复 → 全部测试通过 → 部署上线 → 契约归档）    │
└─────────────────────────────────────────────────────────────────────────┘
```

**关键原则**：

- **后端先行**：后端完成独立交付（接口就绪、文档一致、测试通过）后，前端再启动开发
- **独立审查**：契约编写、代码开发、测试执行、成果审查等关键环节，建议使用独立的 AI 对话窗口，避免上下文污染和自我验证偏差
- **契约冻结**：项目上线后，本次需求的交付契约正式冻结，作为该版本最终的需求依据、技术实现依据及质量验收标准
- **按需裁剪**：实际开发中应结合需求类型、改动范围、影响程度灵活裁剪流程，遵循「按需编写、按影响范围执行、按风险程度验收」的原则

详细的时序图见 [docs/03-整体流程时序图.md](docs/03-整体流程时序图.md)。

## 快速开始

### 新项目从零开始

1. **项目上下文初始化**：让 AI 读取 [skill-01](skills/skill-01-project-context-initialization.md)，完成项目上下文文档的建立
2. **需求沟通与等级判定**：让 AI 读取 [skill-02](skills/skill-02-requirement-level-evaluation.md)，判定需求等级
3. **按等级选择流程**：
   - **L1**：使用 [skill-03](skills/skill-03-l1-lightweight-delivery.md) 执行轻量级交付
   - **L2/L3**：依次使用 skill-04 至 skill-16 执行完整交付流程

### 存量项目接入

1. 先让 AI 读取 [skill-01](skills/skill-01-project-context-initialization.md)，分析现有代码并生成项目上下文文档
2. 开发者审核、修正项目上下文，确保准确
3. 后续流程与新项目一致

### 多人协作建议

- 若团队已统一采用本方法论，建议将项目上下文和交付契约一并提交到代码仓库，统一版本管理
- 若团队尚未建立统一规范，建议仅在本地维护，避免他人误操作或产生困惑

## 适用场景与流程裁剪

本流程是面向前后端协同开发场景制定的**标准参考**，不意味着每项需求都必须严格执行全部步骤。

| 场景 | 建议裁剪方式 |
|------|-------------|
| 仅涉及后端代码优化/重构，不涉及业务规则变更 | 省略产品契约，直接进入后端技术契约与测试契约 |
| 仅涉及后端内部模块调整，不涉及前端交互 | 仅执行后端交付流程，无需引入前端独立交付 |
| 仅涉及前端页面样式/文案调整，不涉及接口变更 | 可简化为轻量级交付或 L1 流程 |
| 紧急 Bug 修复 | 视影响范围决定，小范围修复可简化为 L1 流程 |

**无论采用何种流程，都应确保**：需求边界明确、技术方案经过确认、测试范围覆盖实际影响，并具备明确、可验证的交付标准。
