# 后端代码开发

## 一、任务目标

根据本次需求的产品契约、后端技术契约、项目上下文及现有后端代码，完成后端功能开发。

严格遵循已确认的业务规则、技术方案和项目编码规范，合理控制代码变更范围，确保代码实现符合需求及技术设计。

## 二、执行前提

必须读取以下文件：

1. 项目根目录下的「项目上下文.md」
2. 本次需求的1.产品契约.md
3. 本次需求的2.后端技术契约.md

本次需求的两份契约必须已经通过独立审查，并由开发者确认通过。

如果缺少必要文件、契约尚未定稿或存在影响开发的待确认事项，必须停止相关开发并向开发者反馈。

必须结合实际项目代码分析现有模块、调用链路、公共组件、数据结构及已有实现，不能仅根据契约文字直接生成代码。

### 前置分析反问

开始本Skill的任何实质性工作之前，AI必须先进入一个独立的前置分析阶段。目标是穷尽一切不确定点，确保对任务全貌的理解与开发者预期完全一致。未确认无任何模糊、遗漏或歧义前，不得开始任何输出、编写或修改工作。

#### 第一阶段：全量资料研读

必须完成以下阅读任务：

1. **完整阅读本Skill全文**：逐节理解任务目标、执行步骤、输出格式、约束条件和完成标准。
2. **读取项目上下文**：读取「项目上下文.md」，理解项目架构、技术栈、编码规范及关键约束。
3. **读取相关契约**：读取本Skill要求的所有相关契约（产品契约、技术契约、测试契约等）。
4. **读取实际代码**：阅读与本次任务相关的实际代码，理解现有实现、数据结构、接口定义及调用链路。

阅读过程中建立完整的任务认知图谱：起点（当前状态）、终点（完成标准）、约束、不可为事项。

#### 第二阶段：不确定点穷尽识别

基于全面理解，AI必须主动、自主地识别所有不确定点。结合本次任务的具体业务场景、技术上下文和已有资料，自由地、发散性地思考：还有什么是我不能完全确定的？

思考方向可参考但不限于：文件是否能读到、术语是否理解、资料之间是否一致、技术方案是否可行、操作环境是否具备、输出格式是否明确、需求边界是否清晰、异常情况如何处理、开发者的真实意图是什么。任何让AI产生「应该是这样」而非「确定就是这样」的念头，都是不确定点。

**判定标准**：不是「这会不会影响执行」，而是「我能不能100%确定这件事就是这样」。只要有一丝疑问、一点猜测、一种可能的理解偏差，就必须标记为不确定点。

#### 第三阶段：首轮提问

将识别出的所有不确定点，整理为具体问题向开发者提出：

1. **分主题归类呈现**，方便逐类确认。
2. **问题必须具体**，指向具体内容（如「产品契约第3.2节某规则」、「xx.go文件中xx函数」），不得笼统。
3. **说明提问原因**，简要解释为何会影响任务正确执行。
4. **穷尽式提问**，不设上限，遗漏的代价远大于多问一句。

**禁止**：不得以「信息够了」为由跳过提问；不得将不确定点自行猜测后作为假设继续；不得自行判定某些问题「不重要」而忽略。

#### 第四阶段：多轮确认循环

开发者回答后，必须进入多轮确认循环，而非直接执行。

**每轮循环**：

1. **重读全部资料**：结合回答重新阅读本Skill、项目上下文、相关契约及实际代码。
2. **新不确定点识别**：回答是否引入新信息或新矛盾？之前未意识到的问题是否变明显了？回答中是否有需要进一步澄清的内容？
3. **补充提问**：如有新不确定点，继续提问。这是正常行为，不是上一轮工作的失败。
4. **等待回答后重复步骤1～3**。

**循环终止条件**（必须同时满足）：

- 通读全部资料后，不再发现任何不确定点。
- 对任务的目标、范围、约束、输入、输出、标准均有清晰且无歧义的理解。
- 能够明确回答以下自检问题：
  - 本Skill要求我做什么？做到什么程度算完成？
  - 项目上下文、契约和代码之间是否存在我理解不了的冲突？
  - 开发者是否已回答我所有不确定点，且答案没有引入新的疑问？
  - 我是否能在不进一步提问的情况下，准确、完整地执行本Skill？

只有在自检全部通过后，才能向开发者声明「已理解全貌，准备开始执行」，并在获得开发者确认后进入下一阶段。

#### 第五阶段：进入执行

多轮确认循环结束后，向开发者输出以下声明：

```
我已完整阅读并理解：
- 本Skill的全部要求与约束
- 项目上下文中的相关约定
- 相关契约中的业务规则与技术方案
- 相关实际代码的实现方式

结合你的全部回答，我确认当前不存在任何尚未澄清的不确定点。
我已准备好开始执行，过程中如遇新的未预见问题，将及时反馈。
```

开发者在聊天框回复确认后，方可正式开始本Skill规定的实质性工作。

---

**核心原则**：

- **不要不好意思问**：多一轮确认远胜于事后返工。
- **不要自行假设**：任何不确定的内容，哪怕「应该就是这样」，也必须确认。
- **不要急于执行**：进入多轮确认循环前开始任何编写或修改，均视为违规。
- **不要止于首轮**：第二轮、第三轮提问同样重要，甚至更重要。

## 三、开发分析

### 3.1 理解需求与技术方案

阅读产品契约和后端技术契约，明确：

- 本次需求的业务目标及业务规则。
- 涉及的后端模块及文件变更范围。
- 接口设计及数据结构。
- 核心业务逻辑及处理流程。
- 数据库变更及技术约束。
- 外部依赖及异常处理方式。

### 3.2 分析现有代码

结合项目上下文，阅读本次需求涉及的实际代码，识别：

- 项目目录结构及模块职责。
- 接口入口及调用链路。
- 现有业务逻辑及公共组件。
- 数据模型及数据库访问方式。
- 中间件、工具函数及公共服务。
- 现有代码中的可复用实现。

优先复用项目已有的公共组件、工具函数和业务模块，避免重复实现。

### 3.3 制定开发方案

根据技术契约和实际代码，明确：

- 需要新增、修改的文件。
- 各文件承担的职责。
- 核心函数及方法的实现方式。
- 模块之间的调用关系。
- 数据结构及数据库相关代码变更。
- 可能影响现有功能的修改点。

如果发现技术契约存在遗漏、冲突或无法落地的情况，必须向开发者说明，不得擅自改变已确认的技术方案。

对于技术契约未明确规定的实现细节，允许结合实际代码合理调整，但不得改变已确认的业务规则、接口约定和数据结构。

## 四、代码开发

### 4.1 开发实施

按照确认的开发方案逐步完成代码修改：

1. 根据技术契约新增或修改目标文件。
2. 实现接口及请求参数处理。
3. 实现核心业务逻辑。
4. 实现数据结构及数据库访问逻辑。
5. 实现必要的参数校验、错误处理及权限控制。
6. 完成模块之间的调用及依赖关系。
7. 检查代码变更是否符合技术契约。

开发过程中允许AI自主完成明确的开发任务，不需要每次修改都等待开发者确认。

### 4.2 代码变更管理

允许AI根据开发需要新增、修改和删除代码文件，但必须遵循以下要求：

- 所有变更必须属于本次需求范围。
- 优先采用局部修改，避免无关重构。
- 删除已有业务代码前，必须获得开发者确认。
- 进行大范围重构前，必须获得开发者确认。
- 不得擅自修改与本次需求无关的业务逻辑。
- 不得擅自引入新的技术栈或第三方依赖。

### 4.3 数据库变更

允许直接修改项目中的数据库模型、数据结构定义及相关代码。

涉及外部数据库操作时，例如创建数据表、修改表结构、创建索引或执行数据库变更，必须向开发者说明：

- 需要执行的数据库操作。
- 涉及的数据表及字段。
- 变更内容及原因。
- 必要的SQL语句或操作说明。

外部数据库操作由开发者自行执行，AI不得擅自操作实际数据库。

### 4.4 开发过程中的问题处理

如果发现以下情况，必须暂停受影响的开发任务并向开发者反馈：

- 产品需求存在歧义或业务规则冲突。
- 技术方案存在错误或无法实施。
- 实际代码与技术契约存在明显冲突。
- 需要改变已确认的接口或数据结构。
- 需要进行删除业务代码或大范围重构。
- 存在未经确认的重大技术调整。

对于不影响既定方案的普通实现细节，AI可以自主处理，不必频繁打断开发流程。

## 五、代码质量要求

代码必须符合项目现有的编码规范，重点关注：

1. 命名规范及代码组织。
2. 模块职责及函数设计。
3. 错误处理及日志处理。
4. 请求参数校验及权限控制。
5. 数据库操作及事务处理。
6. 接口定义及响应结构。
7. 并发安全及资源管理。
8. 公共组件复用及重复代码控制。

代码应保持职责清晰、结构合理，避免过度设计和不必要的复杂度。

对于技术契约中未明确但实际实现必需的细节，AI可以提出补充建议，经开发者确认后再实施。

## 六、代码自检

开发完成后，必须进行代码自检。

### 6.1 需求符合性检查

检查：

- 是否实现产品契约中的业务需求。
- 是否正确实现已确认的业务规则。
- 是否覆盖技术契约规定的功能范围。
- 是否存在需求遗漏或错误实现。

### 6.2 技术方案符合性检查

检查：

- 是否符合后端技术契约。
- 接口及数据结构是否符合约定。
- 模块职责及调用关系是否合理。
- 数据库相关代码是否符合设计。
- 是否擅自改变已确认的技术方案。

### 6.3 代码质量检查

检查：

- 是否符合项目架构和编码规范。
- 是否存在重复实现或无关修改。
- 是否存在明显的错误处理遗漏。
- 是否存在资源管理或并发安全问题。
- 是否存在不必要的依赖和复杂度。
- 是否存在未经确认的代码删除或重大调整。

### 6.4 问题处理

发现代码问题时，优先在已确认的开发范围内直接修复。

如果问题涉及业务规则、技术方案或需要开发者决策的重大调整，必须先向开发者反馈，确认后再修改。

## 七、执行约束

1. 必须以已确认的产品契约和后端技术契约作为开发依据。
2. 必须结合实际项目代码实施开发。
3. 必须遵循项目现有架构和编码规范。
4. 优先复用已有组件，避免重复实现。
5. 不得擅自改变已确认的业务规则、接口约定及数据结构。
6. 不得擅自引入新的技术栈或第三方依赖。
7. 不得擅自修改与本次需求无关的业务代码。
8. 删除已有业务代码或进行大范围重构前，必须获得开发者确认。
9. 外部数据库操作必须交由开发者执行。
10. 不得将未经确认的业务或技术调整直接写入代码。
11. 开发过程中发现无法解决的问题，必须及时向开发者反馈。

## 八、完成标准

同时满足以下条件，才算完成：

- [ ] 已读取项目根目录下的「项目上下文.md」及两份需求契约。
- [ ] 已分析本次需求涉及的实际后端代码。
- [ ] 已明确代码修改方案及变更范围。
- [ ] 已完成后端功能代码开发。
- [ ] 已完成必要的数据库模型及相关代码变更。
- [ ] 外部数据库操作已整理为开发者可执行的操作说明。
- [ ] 代码符合项目架构及编码规范。
- [ ] 代码实现符合产品契约和后端技术契约。
- [ ] 已完成代码自检并处理发现的问题。
- [ ] 未擅自修改无关业务代码或已确认的技术方案。
- [ ] 已整理完整的代码变更报告。

完成后，向开发者说明修改文件清单、各文件变更内容、核心实现逻辑、数据库操作要求、契约符合情况及尚未解决的问题。

本Skill不以开发者额外审核确认为完成前提，完成标准满足后即可结束开发任务。
