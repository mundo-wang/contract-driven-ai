# 后端测试契约编写

## 一、任务目标

根据本次需求的产品契约、后端技术契约、项目上下文及现有后端代码，制定完整的后端测试方案。

明确测试范围、测试策略、测试用例、核心场景、数据库验证及测试数据要求，确保本次后端开发成果能够得到有效验证。

## 二、执行前提

必须读取以下文件：

1. 项目根目录下的"项目上下文.md"
2. 本次需求的1.产品契约.md
3. 本次需求的2.后端技术契约.md

如果产品契约或后端技术契约尚未定稿，必须停止编写，要求开发者先完成前置契约确认。

如果缺少必要文件或存在影响测试设计的待确认事项，主动向开发者提问，不得自行假设。

### 前置分析反问

开始执行前，AI必须先完成以下步骤：

1. **资料分析**：仔细阅读本Skill要求读取的全部资料，包括项目上下文、相关契约及实际代码，全面理解本次任务的范围、目标和约束。
2. **识别不确定点**：基于资料分析，主动识别以下类型的问题：
   - 资料之间存在矛盾、冲突或不一致的地方。
   - 契约、代码或文档中存在模糊、遗漏或无法确认的内容。
   - 本Skill的流程、标准或要求与当前项目实际情况可能存在不匹配的地方。
   - 开发者可能尚未明确说明，但对本次任务执行有实质性影响的约束、例外或特殊要求。
3. **列举并提问**：将识别出的不确定点整理为具体问题，向开发者提问。提问应聚焦影响任务正确性的关键问题，避免重复询问已经明确的信息。
4. **确认后执行**：开发者解答后，AI以解答为准开展后续工作。如经分析后不存在不确定点，可直接开始执行。

## 三、测试分析

### 3.1 理解需求与技术方案

阅读产品契约和后端技术契约，明确：

- 本次需求的业务规则及验收标准。
- 涉及的后端模块及接口。
- 核心业务逻辑及数据处理过程。
- 数据结构及数据库变更。
- 技术约束及异常处理方式。

### 3.2 分析现有代码

结合项目上下文，阅读本次需求涉及的实际代码，识别：

- 接口入口及调用链路。
- 核心业务处理逻辑。
- 参数校验及错误处理。
- 数据库读写及事务处理。
- 权限及身份认证逻辑。
- 现有测试代码及可复用测试组件。

测试方案必须结合实际代码制定，不能仅根据契约中的文字描述编写。

### 3.3 识别测试场景

根据业务和技术实现，主动识别以下测试场景：

- 正常业务场景。
- 异常业务场景。
- 边界条件。
- 请求参数校验。
- 身份认证及权限校验。
- 数据正确性。
- 数据库变更及持久化。
- 幂等性及并发场景（业务需要时）。

对于契约中遗漏的测试场景，允许提出补充建议，由开发者确认后纳入正式测试契约。

## 四、测试契约编写

测试契约分为最小必要集和可选扩展集。

优先完成最小必要集，根据需求实际情况补充可选扩展内容。

### 4.1 最小必要集

#### 1. 测试范围

明确本次需要测试的模块、接口、业务逻辑及数据库变更，说明不在本次测试范围内的内容。

#### 2. 测试策略

说明采用的测试类型、测试方式及测试重点，例如单元测试、接口集成测试和数据库验证。

#### 3. 测试用例

每个测试用例必须明确：

- 用例名称。
- 测试目的。
- 前置条件。
- 测试输入或操作步骤。
- 预期结果。

测试步骤必须具体，预期结果必须能够客观判断是否通过。

#### 4. 核心场景覆盖

明确正常流程、异常流程、边界条件及关键业务规则的覆盖情况。

避免只覆盖正常流程而忽略异常情况。

#### 5. 数据库验证

明确需要验证的数据表、数据字段及数据变化，检查新增、修改、删除等操作是否符合业务要求。

#### 6. 测试数据要求

说明测试所需的初始化数据、关联数据、特殊数据及数据清理要求。

### 4.2 可选扩展集

根据需求实际情况选择性补充：

1. 性能测试：验证接口响应时间、处理能力等指标。
2. 安全测试：验证身份认证、权限控制及输入安全。
3. 并发测试：验证并发访问下的数据一致性及业务正确性。
4. 回归测试范围：明确本次变更可能影响的既有功能及需要重新验证的场景。

不涉及的内容无需强行补充。

## 五、文档管理

### 5.1 固定目录

后端测试契约与产品契约、后端技术契约放在同一个需求版本目录下：

```text
交付契约/
└── 需求名称/
    └── v1/
        ├── 1.产品契约.md
        ├── 2.后端技术契约.md
        └── 3.后端测试契约.md
```

### 5.2 版本管理

1. 新需求使用对应的v1目录。
2. 需求迭代使用开发者指定的新版本目录。
3. 历史版本必须保留，不得直接覆盖。
4. 新版本必须生成完整的后端测试契约，不能只记录本次变更内容。

## 六、审核与迭代

测试契约初稿完成后，必须经过审核。

### 6.1 AI自检

检查：

- 测试范围是否覆盖本次需求。
- 测试策略是否符合实际技术实现。
- 核心业务场景是否覆盖完整。
- 正常、异常及边界场景是否遗漏。
- 测试用例是否具备明确的执行步骤。
- 预期结果是否可验证。
- 数据库验证是否完整。
- 测试数据要求是否明确。
- 是否存在重复或无效用例。

### 6.2 开发者审核

向开发者展示测试契约初稿及待确认事项，收集修改意见。

对于AI发现但契约尚未覆盖的测试场景，说明补充原因，由开发者确认。

### 6.3 一致性检查

每次修改完成后，必须重新检查：

1. 测试范围是否符合产品契约。
2. 测试用例是否覆盖产品契约中的业务规则和验收标准。
3. 测试用例是否覆盖后端技术契约中的接口、数据结构及核心业务逻辑。
4. 数据库验证是否符合技术契约中的数据库设计。
5. 测试策略是否符合项目现有架构及编码规范。
6. 是否存在与实际代码不一致的测试设计。
7. 是否存在未经确认的测试要求。

发现冲突或无法确认的内容时，主动向开发者反馈，不得自行决定。

重复执行修改、检查和审核，直到开发者确认定稿。

## 七、执行约束

1. 必须以产品契约、后端技术契约及项目上下文作为测试设计依据。
2. 每个测试用例必须能够追溯到具体业务规则、验收标准或技术设计。
3. 不得遗漏正常、异常及边界场景。
4. 不得使用无法验证的预期结果。
5. 不得将未经确认的测试建议直接写入正式契约。
6. 不得擅自修改产品契约和后端技术契约。
7. 不得擅自修改业务代码及其他非目标文档。
8. 不得覆盖历史版本测试契约。
9. 未经开发者确认，不得宣称测试契约已经定稿。

## 八、完成标准

同时满足以下条件，才算完成：

- [ ] 已读取项目根目录下的"项目上下文.md"及两份前置契约。
- [ ] 已完成相关后端代码分析。
- [ ] 已明确测试范围和测试策略。
- [ ] 已完成最小必要集。
- [ ] 必要的可选扩展内容已补充。
- [ ] 核心测试用例具备明确步骤及可验证的预期结果。
- [ ] 测试用例能够追溯到产品需求或技术设计。
- [ ] 测试契约已存放在规定目录。
- [ ] 已完成AI自检及一致性检查。
- [ ] 开发者已审核并确认定稿。

完成后，向开发者说明测试契约的存放位置、测试覆盖范围及主要测试策略。
