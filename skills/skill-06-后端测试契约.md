# 后端测试契约编写

## 一、任务目标

本阶段属于**事前设计**，在代码开发之前制定测试方案。

根据本次需求的产品契约、后端技术契约、项目上下文，参考项目现有测试实践及编码规范，制定完整的后端测试方案。

明确测试范围、测试策略、测试用例、核心场景、数据库验证及测试数据要求，确保本次后端开发成果未来能够得到有效验证。测试契约描述的是「未来要验证什么」，而非验证「已有代码是否正确」。

## 二、执行前提

必须读取以下文件：

1. 项目根目录下的「项目上下文.md」
2. 本次需求的1.产品契约.md
3. 本次需求的2.后端技术契约.md

同时阅读项目现有测试代码，了解现有测试框架、测试组织方式及可复用测试组件。

如果产品契约或后端技术契约尚未定稿，必须停止编写，要求开发者先完成前置契约确认。

如果缺少必要文件或存在影响测试设计的待确认事项，主动向开发者提问，不得自行假设。

## 前置执行要求

开展本Skill任何实质性工作前，必须严格按以下顺序执行，**不得跳过**：

1. **读取前置反问Skill**：在项目中找到并完整阅读全局Skill「前置反问环节.md」。
2. **执行前置分析**：严格按照该Skill的五阶段流程（资料研读→不确定性识别→首轮提问→多轮确认→执行声明）完成全部步骤。
3. **获得确认**：向开发者输出执行前声明，获得其明确回复确认后，方可开始本Skill的实质性工作。

**禁止**：未读完全局Skill、未完成前置分析流程、未获得开发者确认前，开始任何输出、编写或修改。

## 三、测试分析

### 3.1 理解需求与技术方案

阅读产品契约和后端技术契约，明确：

- 本次需求的业务规则及验收标准。
- 涉及的后端模块及接口。
- 核心业务逻辑及数据处理过程。
- 数据结构及数据库变更。
- 技术约束及异常处理方式。

### 3.2 分析项目现有测试实践

结合项目上下文，阅读项目现有测试代码及相关规范，识别：

- 现有测试框架及测试组织方式。
- 可复用测试工具及公共测试组件。
- 现有测试用例的编写风格及断言方式。
- 项目编码规范中与测试相关的约定。

此时新功能代码尚未开发，不要试图寻找或验证本次需求对应的业务代码实现。

测试方案必须基于后端技术契约制定，同时参考项目现有测试实践，确保测试策略与项目风格一致。

### 3.3 识别测试场景

根据业务和技术实现，主动识别以下测试场景：

- 正常业务场景。
- 异常业务场景。
- 边界条件。
- 请求参数校验。
- 身份认证及权限校验。
- 数据正确性。
- 数据库变更及持久化。
- 幂等性及并发场景（业务需要时）。

对于契约中遗漏的测试场景，允许提出补充建议，由开发者确认后纳入正式测试契约。

## 四、测试契约编写

测试契约分为最小必要集和可选扩展集，提供的是维度参考而非封闭清单。AI应根据需求实际上下文进行推理判断，避免机械套用。

### 4.0 章节结构推断

在编写具体内容前，先分析测试需求特征并确定章节结构：

1. **测试特征提取**：从产品契约、技术契约和代码分析中提取关键特征标签（如涉及性能指标、安全验证、并发操作、公共模块变更等）。
2. **最小必要集保底**：以下核心维度必须全部覆盖——测试范围、测试策略、测试用例、核心场景覆盖、数据库验证、测试数据要求。
3. **可选扩展集筛选**：根据特征标签正向选取相关扩展维度（性能测试、安全测试、并发测试、回归测试范围），反向排除明显无关的维度。
4. **缺口识别**：检查测试需求的每个重要方面是否都有章节承载，如发现「无章节可归」的重要内容，必须主动新增章节并说明理由。
5. **精简校验**：确认无冗余章节，确保契约厚度与需求复杂度匹配。

输出计划编写的章节清单（格式：「章节名 → 选取理由」），确认后开始正式编写。

优先完成最小必要集，根据需求实际情况补充可选扩展内容。

### 4.1 最小必要集

#### 1. 测试范围

明确本次需要测试的模块、接口、业务逻辑及数据库变更，说明不在本次测试范围内的内容。

#### 2. 测试策略

说明采用的测试类型、测试方式及测试重点，例如单元测试、接口集成测试和数据库验证。

#### 3. 测试用例

每个测试用例必须明确：

- 用例编号：按照测试执行顺序从1开始自增编号。
- 用例名称。
- 测试目的。
- 前置条件。
- 测试输入或操作步骤。
- 预期结果。

测试步骤必须具体，预期结果必须能够客观判断是否通过。

测试用例应按照接口调用链路或业务流程的执行顺序排列。先写前置依赖和初始化操作，再写主流程的正向测试，最后写异常流程和边界条件。避免将同一流程的不同步骤拆散或用例编号跳跃。

#### 4. 核心场景覆盖

明确正常流程、异常流程、边界条件及关键业务规则的覆盖情况。

避免只覆盖正常流程而忽略异常情况。

#### 5. 数据库验证

明确需要验证的数据表、数据字段及数据变化，检查新增、修改、删除等操作是否符合业务要求。

#### 6. 测试数据要求

说明测试所需的初始化数据、关联数据、特殊数据及数据清理要求。

### 4.2 可选扩展集

根据需求实际情况选择性补充：

1. 性能测试：验证接口响应时间、处理能力等指标。
2. 安全测试：验证身份认证、权限控制及输入安全。
3. 并发测试：验证并发访问下的数据一致性及业务正确性。
4. 回归测试范围：明确本次变更可能影响的既有功能及需要重新验证的场景。

不涉及的内容无需强行补充。

## 五、文档管理

### 5.1 固定目录

后端测试契约与产品契约、后端技术契约放在同一个需求版本目录下：

```text
交付契约/
└── 需求名称/
    └── v1/
        ├── 1.产品契约.md
        ├── 2.后端技术契约.md
        └── 3.后端测试契约.md
```

### 5.2 版本管理

1. 新需求使用对应的v1目录。
2. 需求迭代使用开发者指定的新版本目录。
3. 历史版本必须保留，不得直接覆盖。
4. 新版本必须生成完整的后端测试契约，不能只记录本次变更内容。

## 六、审核与迭代

测试契约初稿完成后，必须经过审核。

### 6.1 AI自检

检查：

- 测试范围是否覆盖本次需求。
- 测试策略是否符合实际技术实现。
- 核心业务场景是否覆盖完整。
- 正常、异常及边界场景是否遗漏。
- 测试用例是否具备明确的执行步骤。
- 预期结果是否可验证。
- 数据库验证是否完整。
- 测试数据要求是否明确。
- 是否存在重复或无效用例。

### 6.2 开发者审核

向开发者展示测试契约初稿及待确认事项，收集修改意见。

对于AI发现但契约尚未覆盖的测试场景，说明补充原因，由开发者确认。

### 6.3 一致性检查

每次修改完成后，必须重新检查：

1. 测试范围是否符合产品契约。
2. 测试用例是否覆盖产品契约中的业务规则和验收标准。
3. 测试用例是否覆盖后端技术契约中的接口、数据结构及核心业务逻辑。
4. 数据库验证是否符合技术契约中的数据库设计。
5. 测试策略是否符合项目现有架构及编码规范。
6. 测试设计是否与技术契约中的设计方案一致。
7. 是否存在未经确认的测试要求。

发现冲突或无法确认的内容时，主动向开发者反馈，不得自行决定。

重复执行修改、检查和审核，直到开发者确认定稿。

## 七、执行约束

1. 必须以产品契约、后端技术契约及项目上下文作为测试设计依据。
2. 每个测试用例必须能够追溯到具体业务规则、验收标准或技术设计。
3. 不得遗漏正常、异常及边界场景。
4. 不得使用无法验证的预期结果。
5. 不得将未经确认的测试建议直接写入正式契约。
6. 不得擅自修改产品契约和后端技术契约。
7. 不得擅自修改业务代码及其他非目标文档。
8. 不得覆盖历史版本测试契约。
9. 未经开发者确认，不得宣称测试契约已经定稿。

## 八、完成标准

同时满足以下条件，才算完成：

- [ ] 已读取项目根目录下的「项目上下文.md」及两份前置契约。
- [ ] 已完成项目现有测试实践分析。
- [ ] 已明确测试范围和测试策略。
- [ ] 已完成最小必要集。
- [ ] 必要的可选扩展内容已补充。
- [ ] 核心测试用例具备明确步骤及可验证的预期结果。
- [ ] 测试用例能够追溯到产品需求或技术设计。
- [ ] 测试契约已存放在规定目录。
- [ ] 已完成AI自检及一致性检查。
- [ ] 开发者已审核并确认定稿。

完成后，向开发者说明测试契约的存放位置、测试覆盖范围及主要测试策略。
