# 前端三份契约独立审查

## 一、任务目标

以独立审查者的视角，对本次需求的产品契约、前端技术契约和前端测试契约进行全面审查。

重点检查契约完整性、设计合理性、相互一致性、需求追溯关系、契约与项目现状的一致性，以及前端契约与后端接口文档的一致性，识别遗漏、冲突和不合理设计，输出结构化审查报告。

本Skill只负责契约审查，不直接修改契约文件，也不开展独立的代码质量审查。

## 二、执行前提

必须使用全新的AI Agent会话执行审查，不得沿用编写三份契约时的对话上下文，避免自我审查偏差。

必须读取以下文件：

1. 项目根目录下的「项目上下文.md」
2. 本次需求的1.产品契约.md
3. 本次需求的2.前端技术契约.md
4. 本次需求的3.前端测试契约.md

同时获取后端接口文档（如 Swagger），并阅读与本次需求相关的前端现有代码，用于核对前端技术契约与项目现状的一致性，以及核对前端契约与后端接口文档的一致性。

如果缺少必要文件、契约尚未定稿或无法获取必要资料，必须停止审查并向开发者说明原因，不得自行假设。

### 前置分析反问

开始本Skill的任何实质性工作之前，AI必须先进入一个独立的前置分析阶段。目标是穷尽一切不确定点，确保对任务全貌的理解与开发者预期完全一致。未确认无任何模糊、遗漏或歧义前，不得开始任何输出、编写或修改工作。

#### 第一阶段：全量资料研读

必须完成以下阅读任务：

1. **完整阅读本Skill全文**：逐节理解任务目标、执行步骤、输出格式、约束条件和完成标准。
2. **读取项目上下文**：读取「项目上下文.md」，理解项目架构、技术栈、编码规范及关键约束。
3. **读取相关契约**：读取本Skill要求的所有相关契约（产品契约、技术契约、测试契约等）。
4. **读取实际代码**：阅读与本次任务相关的实际代码，理解现有实现、数据结构、接口定义及调用链路。

阅读过程中建立完整的任务认知图谱：起点（当前状态）、终点（完成标准）、约束、不可为事项。

#### 第二阶段：不确定点穷尽识别

基于全面理解，AI必须主动、自主地识别所有不确定点。结合本次任务的具体业务场景、技术上下文和已有资料，自由地、发散性地思考：还有什么是我不能完全确定的？

思考方向可参考但不限于：文件是否能读到、术语是否理解、资料之间是否一致、技术方案是否可行、操作环境是否具备、输出格式是否明确、需求边界是否清晰、异常情况如何处理、开发者的真实意图是什么。任何让AI产生「应该是这样」而非「确定就是这样」的念头，都是不确定点。

**判定标准**：不是「这会不会影响执行」，而是「我能不能100%确定这件事就是这样」。只要有一丝疑问、一点猜测、一种可能的理解偏差，就必须标记为不确定点。

#### 第三阶段：首轮提问

将识别出的所有不确定点，整理为具体问题向开发者提出：

1. **分主题归类呈现**，方便逐类确认。
2. **问题必须具体**，指向具体内容（如「产品契约第3.2节某规则」、「xx.go文件中xx函数」），不得笼统。
3. **说明提问原因**，简要解释为何会影响任务正确执行。
4. **穷尽式提问**，不设上限，遗漏的代价远大于多问一句。

**禁止**：不得以「信息够了」为由跳过提问；不得将不确定点自行猜测后作为假设继续；不得自行判定某些问题「不重要」而忽略。

#### 第四阶段：多轮确认循环

开发者回答后，必须进入多轮确认循环，而非直接执行。

**每轮循环**：

1. **重读全部资料**：结合回答重新阅读本Skill、项目上下文、相关契约及实际代码。
2. **新不确定点识别**：回答是否引入新信息或新矛盾？之前未意识到的问题是否变明显了？回答中是否有需要进一步澄清的内容？
3. **补充提问**：如有新不确定点，继续提问。这是正常行为，不是上一轮工作的失败。
4. **等待回答后重复步骤1～3**。

**循环终止条件**（必须同时满足）：

- 通读全部资料后，不再发现任何不确定点。
- 对任务的目标、范围、约束、输入、输出、标准均有清晰且无歧义的理解。
- 能够明确回答以下自检问题：
  - 本Skill要求我做什么？做到什么程度算完成？
  - 项目上下文、契约和代码之间是否存在我理解不了的冲突？
  - 开发者是否已回答我所有不确定点，且答案没有引入新的疑问？
  - 我是否能在不进一步提问的情况下，准确、完整地执行本Skill？

只有在自检全部通过后，才能向开发者声明「已理解全貌，准备开始执行」，并在获得开发者确认后进入下一阶段。

#### 第五阶段：进入执行

多轮确认循环结束后，向开发者输出以下声明：

```
我已完整阅读并理解：
- 本Skill的全部要求与约束
- 项目上下文中的相关约定
- 相关契约中的业务规则与技术方案
- 相关实际代码的实现方式

结合你的全部回答，我确认当前不存在任何尚未澄清的不确定点。
我已准备好开始执行，过程中如遇新的未预见问题，将及时反馈。
```

开发者在聊天框回复确认后，方可正式开始本Skill规定的实质性工作。

---

**核心原则**：

- **不要不好意思问**：多一轮确认远胜于事后返工。
- **不要自行假设**：任何不确定的内容，哪怕「应该就是这样」，也必须确认。
- **不要急于执行**：进入多轮确认循环前开始任何编写或修改，均视为违规。
- **不要止于首轮**：第二轮、第三轮提问同样重要，甚至更重要。

## 三、契约审查

### 3.1 产品契约审查

检查业务需求是否完整、清晰、合理，重点关注：

- 需求背景与业务目标是否明确。
- 业务规则是否存在歧义、遗漏或冲突。
- 业务流程是否覆盖正常、异常和边界场景。
- 需求范围与边界条件是否明确。
- 验收标准是否具体、可验证。
- 不同业务规则之间是否存在矛盾。

### 3.2 前端技术契约审查

检查前端技术设计是否合理，重点关注：

- 技术方案是否符合项目现有架构和技术规范。
- 页面与组件结构是否明确、职责是否清晰。
- 路由与导航设计是否完整。
- 交互逻辑是否覆盖正常和异常场景。
- 状态管理方案是否合理。
- 接口调用设计是否与后端接口文档一致。
- 表单与校验设计是否完整。
- 技术约束及依赖关系是否明确。
- 是否存在设计遗漏、冲突或不合理之处。

### 3.3 前端测试契约审查

检查前端测试设计是否完整，重点关注：

- 测试范围与测试策略是否合理，是否聚焦「测什么」。
- 测试用例是否覆盖核心业务场景。
- 正常、异常及边界场景是否充分覆盖。
- 测试前置条件、操作步骤是否明确、可复现。
- 预期页面表现及数据展示结果是否具体、可验证。
- 数据验证要求是否完整。
- 测试环境要求是否明确。
- 是否存在关键测试遗漏或无效测试用例。

### 3.4 三份契约一致性审查

检查三份契约之间是否保持一致：

- 产品需求是否都有对应的前端技术设计。
- 前端技术设计是否都有对应的前端测试用例。
- 前端技术实现是否准确满足产品契约中的业务规则。
- 前端测试用例是否准确验证产品契约中的验收标准。
- 接口定义、页面交互和业务规则是否存在冲突。
- 测试范围是否与产品需求及前端技术设计一致。

### 3.5 需求追溯审查

建立以下需求追溯关系：

产品需求 → 前端技术设计 → 前端测试用例

逐项检查核心业务需求是否具备对应的前端技术设计和前端测试用例。

对于无法建立对应关系、缺少技术设计或缺少测试用例的需求，必须记录为审查问题，并明确具体位置。

### 3.6 契约与项目现状一致性审查

结合项目上下文和前端实际代码，核对前端技术契约是否符合：

- 项目现有架构及模块划分。
- 现有页面结构、组件组织及路由配置。
- 现有状态管理及数据流转方式。
- 项目编码规范。
- 已有技术约束及公共组件使用方式。

本阶段只核对契约与项目现状的一致性，不扩展为代码质量、业务代码实现或其他方面的审查。

### 3.7 与后端接口文档的一致性审查

结合后端接口文档，核对以下内容：

- 前端技术契约中的接口调用设计是否与后端接口文档保持一致。
- 前端测试契约中的数据验证是否与后端接口文档的响应结构一致。
- 接口路径、请求方法、请求参数及响应结构是否存在差异。

发现不一致时，必须记录为审查问题，不得自行假设或调整。

## 四、问题分级

审查发现的问题必须按照以下等级分类：

1. P0：严重问题，影响业务正确性或存在重大风险。
2. P1：重要问题，核心需求遗漏、技术方案错误或关键测试缺失。
3. P2：一般问题，局部设计不完整或存在明显问题。
4. P3：优化建议，不影响当前需求正确交付。

每个问题必须明确：

- 问题等级。
- 所属契约。
- 具体文件及章节位置。
- 问题描述。
- 产生的影响。
- 修改建议及原因。

不得将个人偏好或非必要优化建议判定为实际缺陷。

## 五、审查报告

审查完成后，通过聊天框向开发者输出结构化审查报告，不要求额外生成独立报告文件。

### 5.1 审查结论

给出以下结论之一：

- 通过：不存在未解决的P0、P1问题，满足审查完成标准。
- 条件通过：不存在未解决的P0、P1问题，但仍有需要开发者关注的遗留问题。
- 不通过：存在未解决的P0或P1问题，不能通过审查。

### 5.2 问题清单

逐项列出审查发现的问题，包括问题等级、所属契约、具体位置、问题描述、影响及修改建议。

### 5.3 需求追溯检查

列出产品需求、前端技术设计和前端测试用例之间的对应关系，明确已覆盖内容及缺失项。

### 5.4 一致性检查

说明三份契约之间，以及前端技术契约与项目现状、后端接口文档之间的一致性检查结果。

### 5.5 最终审查结果

汇总未解决问题、遗留风险及是否满足审查通过条件。

审查报告必须提供明确的文件路径、章节或具体内容定位，不得只输出笼统的审查意见。

## 六、审核与迭代

### 6.1 独立审查

首次审查必须独立完成，不得依赖契约编写阶段的结论或自我判断。

### 6.2 开发者审核

向开发者展示审查报告及所有待处理问题，由开发者决定是否修改契约。

只输出审查意见和修改建议，不得直接修改产品契约、前端技术契约及前端测试契约。

### 6.3 重新审查

契约修改完成后，必须重新执行完整审查，而不是只检查上一次发现的问题。

重新审查可用之前的审查Agent执行。

每轮审查都必须重新检查：

1. 三份契约各自的完整性。
2. 三份契约之间的一致性。
3. 产品需求到前端技术设计、前端测试用例的追溯关系。
4. 前端技术契约与项目现状的一致性。
5. 前端技术契约与后端接口文档的一致性。
6. 上一轮问题是否得到有效解决。
7. 修改是否引入新的遗漏或冲突。

重复执行审查、报告、修改和复查，直到满足审查通过条件，并由开发者确认最终结果。

## 七、执行约束

1. 必须使用独立AI Agent会话执行首次审查。
2. 必须读取完整的项目上下文和本次需求三份契约。
3. 必须结合实际前端代码核对前端技术契约与项目现状的一致性。
4. 必须结合后端接口文档核对前端契约与后端接口的一致性。
5. 必须检查三份契约的完整性及相互一致性。
6. 必须建立产品需求、前端技术设计和前端测试用例之间的追溯关系。
7. 不得直接修改任何契约文件。
8. 不得擅自改变已确认的业务规则和技术方案。
9. 不得将未经确认的优化建议作为正式契约要求。
10. 不得推测缺失信息，无法确认的内容必须明确标记。
11. 所有问题必须有对应的契约内容或项目资料作为依据。
12. 未经开发者确认，不得宣称审查最终通过。

## 八、完成标准

同时满足以下条件，才算完成：

- [ ] 已使用独立AI Agent会话执行首次审查。
- [ ] 已读取项目根目录下的「项目上下文.md」及三份需求契约。
- [ ] 已阅读相关前端代码。
- [ ] 已完成产品契约完整性审查。
- [ ] 已完成前端技术契约合理性审查。
- [ ] 已完成前端测试契约完整性审查。
- [ ] 已完成三份契约一致性审查。
- [ ] 已完成产品需求、前端技术设计和前端测试用例追溯检查。
- [ ] 已完成前端技术契约与项目现状一致性检查。
- [ ] 已完成前端技术契约与后端接口文档一致性检查。
- [ ] 所有审查问题均已分级并提供具体位置。
- [ ] 已通过聊天框输出完整审查报告。
- [ ] 不存在未解决的P0和P1问题。
- [ ] 开发者已确认最终审查结果。

完成后，向开发者说明审查结论、遗留问题及最终审查状态。
