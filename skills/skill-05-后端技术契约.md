# 后端技术契约编写

## 一、任务目标

根据本次需求的产品契约、项目上下文及现有后端代码，制定完整、可执行的后端技术实现方案。

明确本次需求涉及的模块、接口、数据结构、数据库变更及核心业务逻辑，为后续后端开发提供明确依据。

后端技术契约只描述技术实现方案，不负责实际编写业务代码。

## 二、执行前提

必须读取以下文件：

1. 项目根目录下的「项目上下文.md」
2. 本次需求对应的1.产品契约.md

如果产品契约尚未定稿，或者存在影响技术设计的待确认事项，必须停止编写并要求开发者先完成确认。

如果缺少必要文件，主动告知开发者，不得自行假设项目架构或业务规则。

## 前置执行要求

开展本Skill任何实质性工作前，必须严格按以下顺序执行，**不得跳过**：

1. **读取前置反问Skill**：在项目中找到并完整阅读全局Skill「前置反问环节.md」。
2. **执行前置分析**：严格按照该Skill的五阶段流程（资料研读→不确定性识别→首轮提问→多轮确认→执行声明）完成全部步骤。
3. **获得确认**：向开发者输出执行前声明，获得其明确回复确认后，方可开始本Skill的实质性工作。

**禁止**：未读完全局Skill、未完成前置分析流程、未获得开发者确认前，开始任何输出、编写或修改。

## 三、技术方案分析

### 3.1 理解业务需求

阅读产品契约，理解本次需求的业务目标、业务规则、业务流程及验收标准。

识别每项业务需求对应的后端技术实现要求。

### 3.2 分析现有代码

结合项目上下文，阅读与本次需求相关的实际代码，重点分析：

- 涉及的业务模块及现有职责。
- 相关接口及调用链路。
- 数据模型及数据库结构。
- 现有业务逻辑及可复用组件。
- 相关外部依赖及服务调用。
- 现有实现方式与编码规范。

不得仅根据项目文档推断代码实现，必须通过实际代码确认。

### 3.3 确定技术方案

根据业务需求和现有代码，分析：

- 需要修改哪些模块及文件。
- 是否需要新增模块、文件或函数。
- 是否需要新增或调整接口。
- 是否需要新增或修改数据结构。
- 是否需要新增或修改数据库表及字段。
- 是否需要调整现有业务逻辑。
- 是否能够复用已有组件及公共能力。

对于存在多种可行方案的关键技术决策，允许提出推荐方案和备选方案，说明各方案的优缺点及影响，由开发者确认后再写入正式契约。

技术设计细化程度根据需求复杂度灵活决定。简单需求可以描述到模块级，复杂需求应明确具体文件路径、关键函数及其职责。

## 四、契约编写

后端技术契约分为最小必要集和可选扩展集，提供的是维度参考而非封闭清单。AI应根据需求实际上下文进行推理判断，避免机械套用。

### 4.0 章节结构推断

在编写具体内容前，先分析技术方案特征并确定章节结构：

1. **方案特征提取**：从产品契约和代码分析中提取关键特征标签（如涉及跨服务调用、缓存、消息队列、事务/一致性、并发、复杂算法、高风险变更等）。
2. **最小必要集保底**：以下核心维度必须全部覆盖——技术方案概述、模块职责与变更、接口设计、数据结构设计、数据库变更、核心业务逻辑、技术约束。
3. **可选扩展集筛选**：根据特征标签正向选取相关扩展维度（依赖服务调用、缓存策略、消息队列、事务与一致性、代码示例、风险评估），反向排除明显无关的维度。
4. **缺口识别**：检查技术方案的每个重要方面是否都有章节承载，如发现「无章节可归」的重要内容，必须主动新增章节并说明理由。
5. **精简校验**：确认无冗余章节，确保契约厚度与需求复杂度匹配。

输出计划编写的章节清单（格式：「章节名 → 选取理由」），确认后开始正式编写。

优先完成最小必要集，根据需求实际情况补充可选扩展内容。

### 4.1 最小必要集

#### 1. 技术方案概述

说明整体实现思路、涉及的技术组件及核心处理流程。

#### 2. 模块职责与变更

明确涉及的模块、模块职责、需要新增或修改的内容，以及模块之间的调用关系。

必要时明确具体文件路径及关键函数职责。

#### 3. 接口设计

明确接口路径、请求方法、请求参数、响应结构、错误码及相关业务约束。

涉及已有接口调整时，说明变更内容及兼容性影响。

#### 4. 数据结构设计

明确涉及的请求结构、响应结构、业务模型及其他必要的数据结构。

#### 5. 数据库变更

明确新增或修改的数据表、字段、类型、索引、约束及相关数据变更要求。

如果不涉及数据库变更，应明确说明。

#### 6. 核心业务逻辑

描述核心业务处理流程、关键判断条件、数据变化及异常处理方式。

#### 7. 技术约束

明确本次开发必须遵循的项目架构、编码规范、技术限制及实现约束。

### 4.2 可选扩展集

根据需求实际情况选择性补充：

1. 依赖服务调用：外部服务的调用方式、参数及异常处理。
2. 缓存策略：缓存数据、缓存键、过期策略及一致性要求。
3. 消息队列：消息结构、生产消费流程及可靠性要求。
4. 事务与一致性：事务边界、数据一致性及并发控制要求。
5. 代码示例：对复杂或容易产生歧义的技术设计提供参考代码。
6. 风险评估：识别技术实现中的潜在风险及应对方案。

不涉及的内容无需强行补充。

## 五、文档管理

### 5.1 固定目录

后端技术契约与产品契约放在同一个需求版本目录下：

```text
交付契约/
└── 需求名称/
    └── v1/
        ├── 1.产品契约.md
        └── 2.后端技术契约.md
```

### 5.2 版本管理

1. 新需求使用对应的v1目录。
2. 已有需求迭代时使用开发者指定的新版本目录。
3. 历史版本必须保留，不得直接覆盖。
4. 新版本必须生成完整的后端技术契约，不能只记录本次变更内容。

## 六、审核与迭代

技术契约初稿完成后，必须经过审核。

### 6.1 AI自检

检查：

- 技术方案是否覆盖产品契约中的业务需求。
- 模块职责及变更是否明确。
- 接口设计是否完整。
- 数据结构及数据库变更是否合理。
- 核心业务逻辑是否覆盖正常和异常场景。
- 是否符合项目现有架构及编码规范。
- 是否存在未经确认的技术决策。
- 是否存在不必要的技术设计。

### 6.2 开发者审核

向开发者展示技术契约初稿及待确认事项，收集修改意见。

对于关键技术方案，必须由开发者确认后才能定稿。

### 6.3 一致性检查

每次修改完成后，必须重新检查：

1. 技术方案是否符合产品契约。
2. 每项技术设计是否能够追溯到具体业务需求。
3. 模块职责是否符合项目架构设计。
4. 接口、数据结构及数据库设计是否相互一致。
5. 是否符合项目编码规范。
6. 是否与现有代码实现冲突。
7. 是否存在未经确认的技术约定。

发现冲突或无法确认的内容时，主动向开发者反馈，不得自行决定。

重复执行修改、检查和审核，直到开发者确认定稿。

## 七、执行约束

1. 必须以产品契约和项目上下文作为技术设计依据。
2. 不得擅自修改产品契约中的业务规则。
3. 不得脱离实际代码设计与项目架构无关的实现方案。
4. 不得擅自引入新的技术栈、第三方依赖或公共组件。
5. 不得将未经确认的技术建议写入正式契约。
6. 每项技术设计必须能够追溯到对应的业务需求。
7. 不得擅自修改业务代码及其他非目标文档。
8. 不得覆盖历史版本技术契约。
9. 未经开发者确认，不得宣称技术契约已经定稿。

## 八、完成标准

同时满足以下条件，才算完成：

- [ ] 已读取项目根目录下的「项目上下文.md」及产品契约。
- [ ] 已完成相关后端代码分析。
- [ ] 已明确本次需求的技术实现方案。
- [ ] 已完成最小必要集。
- [ ] 必要的可选扩展内容已补充。
- [ ] 每项技术设计均可追溯到产品契约。
- [ ] 技术契约已存放在规定目录。
- [ ] 已完成AI自检及一致性检查。
- [ ] 开发者已审核并确认定稿。

完成后，向开发者说明技术契约的存放位置、涉及的核心模块及主要技术变更。
