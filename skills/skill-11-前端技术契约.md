# 前端技术契约编写

## 一、任务目标

根据本次需求的产品契约、后端接口文档、前端项目上下文及现有前端代码，制定完整、可执行的前端技术实现方案。

明确本次需求涉及的页面、组件、路由、交互逻辑、状态管理、接口调用及相关技术约束，为后续前端开发提供明确依据。

前端技术契约只描述技术实现方案，不负责实际编写业务代码。

## 二、执行前提

必须读取以下文件：

1. 项目根目录下的"项目上下文.md"
2. 本次需求的1.产品契约.md

同时获取后端接口文档（如Swagger），并阅读本次需求涉及的前端现有代码。

要求：

- 产品契约必须已经定稿，并由开发者确认通过。
- 后端独立交付必须已完成（审查通过），后端接口已就绪且可正常访问。
- 以后端接口文档为唯一准据，前端技术契约中的接口调用设计必须与后端接口文档保持一致。

如果产品契约尚未定稿、后端接口尚未就绪或缺少必要文件，必须停止编写并向开发者说明原因，不得自行假设。

### 前置分析反问

开始执行前，AI必须先完成以下步骤：

1. **资料分析**：仔细阅读本Skill要求读取的全部资料，包括项目上下文、相关契约及实际代码，全面理解本次任务的范围、目标和约束。
2. **识别不确定点**：基于资料分析，主动识别以下类型的问题：
   - 资料之间存在矛盾、冲突或不一致的地方。
   - 契约、代码或文档中存在模糊、遗漏或无法确认的内容。
   - 本Skill的流程、标准或要求与当前项目实际情况可能存在不匹配的地方。
   - 开发者可能尚未明确说明，但对本次任务执行有实质性影响的约束、例外或特殊要求。
3. **列举并提问**：将识别出的不确定点整理为具体问题，向开发者提问。提问应聚焦影响任务正确性的关键问题，避免重复询问已经明确的信息。
4. **确认后执行**：开发者解答后，AI以解答为准开展后续工作。如经分析后不存在不确定点，可直接开始执行。

## 三、技术方案分析

### 3.1 理解业务需求

阅读产品契约，理解本次需求的业务目标、业务规则、业务流程及验收标准。

识别每项业务需求对应的前端技术实现要求，包括页面展示、用户交互、数据获取及状态变化。

### 3.2 分析现有代码

结合项目上下文，阅读与本次需求相关的前端实际代码，重点分析：

- 页面结构及组件组织方式。
- 路由配置及导航逻辑。
- 状态管理方案（全局状态、局部状态及持久化策略）。
- 接口调用封装及请求响应处理方式。
- 表单处理及校验方式。
- 公共组件、工具函数及样式规范。
- 现有实现方式与编码规范。

不得仅根据项目文档推断代码实现，必须通过实际代码确认。

### 3.3 确定技术方案

根据业务需求、后端接口文档及现有代码，分析：

- 需要新增、修改的页面及组件。
- 各页面及组件承担的职责及相互关系。
- 路由及页面跳转逻辑是否需要调整。
- 状态管理方案是否需要变更。
- 需要调用的后端接口及数据处理方式。
- 表单字段、校验规则及错误提示方式。
- 是否能够复用已有组件及公共能力。
- 是否需要引入新的第三方依赖或组件库。

对于存在多种可行方案的关键技术决策，允许提出推荐方案和备选方案，说明各方案的优缺点及影响，由开发者确认后再写入正式契约。

技术设计细化程度根据需求复杂度灵活决定。简单需求可以描述到页面级，复杂需求应明确具体组件、关键函数及其职责。

## 四、契约编写

前端技术契约分为最小必要集和可选扩展集。

优先完成最小必要集，根据需求实际情况补充可选扩展内容。

### 4.1 最小必要集

#### 1. 技术方案概述

说明整体前端实现思路、涉及的页面与组件及核心处理流程。

#### 2. 页面与组件结构

列出新增或变更的页面及组件，明确各组件的职责、相互关系及数据传递方式。

必要时明确具体文件路径及关键组件职责。

#### 3. 路由与导航

明确新增或变更的路由、页面跳转逻辑及参数传递方式。

#### 4. 交互逻辑

描述用户点击、输入、提交等操作对应的前端处理逻辑及状态变化。

#### 5. 状态管理

明确涉及的全局状态、局部状态、状态流转及持久化策略。

#### 6. 接口调用

列出本次需求涉及的后端接口，明确以下内容：

- 请求参数组装方式。
- 响应数据处理逻辑。
- 异常处理方式。
- 错误码对应的页面反馈策略。

接口调用设计必须与后端接口文档保持一致，不得擅自变更接口路径、请求方法、参数结构或响应格式。如果发现后端接口文档存在遗漏或错误，必须暂停并反馈给开发者确认。

#### 7. 表单与校验

明确表单字段、校验规则及错误提示方式。

#### 8. 技术约束

明确本次开发必须遵循的前端框架规范（如组合式 API 风格）、组件使用约束、样式规范及其他技术限制。

### 4.2 可选扩展集

根据需求实际情况选择性补充：

1. 权限控制：页面级、按钮级的权限判断逻辑，以及无权限时的展示策略。
2. 数据展示规则：列表排序、分页、空状态、加载状态及数据格式化规则。
3. 第三方组件与库：引入的外部组件或依赖库、使用方式及版本要求。
4. 响应式适配：不同屏幕尺寸下的页面布局、组件展示及交互差异。
5. 代码示例：对复杂交互或状态管理提供参考代码。

不涉及的内容无需强行补充。

## 五、文档管理

### 5.1 固定目录

前端技术契约与产品契约放在同一个需求版本目录下：

```text
交付契约/
└── 需求名称/
    └── v1/
        ├── 1.产品契约.md
        └── 2.前端技术契约.md
```

### 5.2 版本管理

1. 新需求使用对应的v1目录。
2. 已有需求迭代时使用开发者指定的新版本目录。
3. 历史版本必须保留，不得直接覆盖。
4. 新版本必须生成完整的前端技术契约，不能只记录本次变更内容。

## 六、审核与迭代

技术契约初稿完成后，必须经过审核。

### 6.1 AI自检

检查：

- 技术方案是否覆盖产品契约中的业务需求。
- 页面与组件结构是否明确。
- 路由与导航设计是否完整。
- 交互逻辑是否覆盖正常和异常场景。
- 接口调用是否与后端接口文档一致。
- 状态管理及表单校验是否合理。
- 是否符合项目现有架构及编码规范。
- 是否存在未经确认的技术决策。
- 是否存在不必要的技术设计。

### 6.2 开发者审核

向开发者展示技术契约初稿及待确认事项，收集修改意见。

对于关键技术方案，必须由开发者确认后才能定稿。

### 6.3 一致性检查

每次修改完成后，必须重新检查：

1. 技术方案是否符合产品契约。
2. 每项技术设计是否能够追溯到具体业务需求。
3. 页面与组件结构是否符合项目架构设计。
4. 接口调用是否与后端接口文档保持一致。
5. 路由、状态管理及交互设计是否相互一致。
6. 是否符合项目编码规范。
7. 是否与现有代码实现冲突。
8. 是否存在未经确认的技术约定。

发现冲突或无法确认的内容时，主动向开发者反馈，不得自行决定。

重复执行修改、检查和审核，直到开发者确认定稿。

## 七、执行约束

1. 必须以产品契约、后端接口文档和项目上下文作为技术设计依据。
2. 不得擅自修改产品契约中的业务规则。
3. 不得脱离实际代码设计与项目架构无关的实现方案。
4. 不得擅自引入新的技术栈、第三方依赖或公共组件。
5. 不得将未经确认的技术建议写入正式契约。
6. 每项技术设计必须能够追溯到对应的业务需求。
7. 不得擅自修改业务代码、产品契约、后端技术契约及其他非目标文档。
8. 不得覆盖历史版本技术契约。
9. 接口调用设计必须与后端接口文档保持一致，不得擅自变更。
10. 发现后端接口文档遗漏或错误时，必须暂停并反馈，不得自行假设或调整。
11. 未经开发者确认，不得宣称技术契约已经定稿。

## 八、完成标准

同时满足以下条件，才算完成：

- [ ] 已读取项目根目录下的"项目上下文.md"、产品契约及后端接口文档。
- [ ] 已完成相关前端代码分析。
- [ ] 已明确本次需求的前端技术实现方案。
- [ ] 已完成最小必要集。
- [ ] 必要的可选扩展内容已补充。
- [ ] 每项技术设计均可追溯到产品契约。
- [ ] 接口调用设计与后端接口文档保持一致。
- [ ] 技术契约已存放在规定目录。
- [ ] 已完成AI自检及一致性检查。
- [ ] 开发者已审核并确认定稿。

完成后，向开发者说明技术契约的存放位置、涉及的核心页面及组件、主要技术变更及与后端接口的对应关系。
