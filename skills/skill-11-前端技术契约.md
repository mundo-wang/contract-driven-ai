# 前端技术契约编写

## 一、任务目标

根据本次需求的产品契约、后端接口文档、前端项目上下文及现有前端代码，制定完整、可执行的前端技术实现方案。

明确本次需求涉及的页面、组件、路由、交互逻辑、状态管理、接口调用及相关技术约束，为后续前端开发提供明确依据。

前端技术契约只描述技术实现方案，不负责实际编写业务代码。

## 二、执行前提

必须读取以下文件：

1. 项目根目录下的「项目上下文.md」
2. 本次需求的1.产品契约.md

同时获取后端接口文档（如Swagger），并阅读本次需求涉及的前端现有代码。

要求：

- 产品契约必须已经定稿，并由开发者确认通过。
- 后端独立交付必须已完成（审查通过），后端接口已就绪且可正常访问。
- 以后端接口文档为唯一准据，前端技术契约中的接口调用设计必须与后端接口文档保持一致。

如果产品契约尚未定稿、后端接口尚未就绪或缺少必要文件，必须停止编写并向开发者说明原因，不得自行假设。

### 前置分析反问

开始本Skill的任何实质性工作之前，AI必须先进入一个独立的前置分析阶段。目标是穷尽一切不确定点，确保对任务全貌的理解与开发者预期完全一致。未确认无任何模糊、遗漏或歧义前，不得开始任何输出、编写或修改工作。

#### 第一阶段：全量资料研读

必须完成以下阅读任务：

1. **完整阅读本Skill全文**：逐节理解任务目标、执行步骤、输出格式、约束条件和完成标准。
2. **读取项目上下文**：读取「项目上下文.md」，理解项目架构、技术栈、编码规范及关键约束。
3. **读取相关契约**：读取本Skill要求的所有相关契约（产品契约、技术契约、测试契约等）。
4. **读取实际代码**：阅读与本次任务相关的实际代码，理解现有实现、数据结构、接口定义及调用链路。

阅读过程中建立完整的任务认知图谱：起点（当前状态）、终点（完成标准）、约束、不可为事项。

#### 第二阶段：不确定点穷尽识别

基于全面理解，AI必须主动、自主地识别所有不确定点。结合本次任务的具体业务场景、技术上下文和已有资料，自由地、发散性地思考：还有什么是我不能完全确定的？

思考方向可参考但不限于：文件是否能读到、术语是否理解、资料之间是否一致、技术方案是否可行、操作环境是否具备、输出格式是否明确、需求边界是否清晰、异常情况如何处理、开发者的真实意图是什么。任何让AI产生「应该是这样」而非「确定就是这样」的念头，都是不确定点。

**判定标准**：不是「这会不会影响执行」，而是「我能不能100%确定这件事就是这样」。只要有一丝疑问、一点猜测、一种可能的理解偏差，就必须标记为不确定点。

#### 第三阶段：首轮提问

将识别出的所有不确定点，整理为具体问题向开发者提出：

1. **分主题归类呈现**，方便逐类确认。
2. **问题必须具体**，指向具体内容（如「产品契约第3.2节某规则」、「xx.go文件中xx函数」），不得笼统。
3. **说明提问原因**，简要解释为何会影响任务正确执行。
4. **穷尽式提问**，不设上限，遗漏的代价远大于多问一句。

**禁止**：不得以「信息够了」为由跳过提问；不得将不确定点自行猜测后作为假设继续；不得自行判定某些问题「不重要」而忽略。

#### 第四阶段：多轮确认循环

开发者回答后，必须进入多轮确认循环，而非直接执行。

**每轮循环**：

1. **重读全部资料**：结合回答重新阅读本Skill、项目上下文、相关契约及实际代码。
2. **新不确定点识别**：回答是否引入新信息或新矛盾？之前未意识到的问题是否变明显了？回答中是否有需要进一步澄清的内容？
3. **补充提问**：如有新不确定点，继续提问。这是正常行为，不是上一轮工作的失败。
4. **等待回答后重复步骤1～3**。

**循环终止条件**（必须同时满足）：

- 通读全部资料后，不再发现任何不确定点。
- 对任务的目标、范围、约束、输入、输出、标准均有清晰且无歧义的理解。
- 能够明确回答以下自检问题：
  - 本Skill要求我做什么？做到什么程度算完成？
  - 项目上下文、契约和代码之间是否存在我理解不了的冲突？
  - 开发者是否已回答我所有不确定点，且答案没有引入新的疑问？
  - 我是否能在不进一步提问的情况下，准确、完整地执行本Skill？

只有在自检全部通过后，才能向开发者声明「已理解全貌，准备开始执行」，并在获得开发者确认后进入下一阶段。

#### 第五阶段：进入执行

多轮确认循环结束后，向开发者输出以下声明：

```
我已完整阅读并理解：
- 本Skill的全部要求与约束
- 项目上下文中的相关约定
- 相关契约中的业务规则与技术方案
- 相关实际代码的实现方式

结合你的全部回答，我确认当前不存在任何尚未澄清的不确定点。
我已准备好开始执行，过程中如遇新的未预见问题，将及时反馈。
```

开发者在聊天框回复确认后，方可正式开始本Skill规定的实质性工作。

---

**核心原则**：

- **不要不好意思问**：多一轮确认远胜于事后返工。
- **不要自行假设**：任何不确定的内容，哪怕「应该就是这样」，也必须确认。
- **不要急于执行**：进入多轮确认循环前开始任何编写或修改，均视为违规。
- **不要止于首轮**：第二轮、第三轮提问同样重要，甚至更重要。

## 三、技术方案分析

### 3.1 理解业务需求

阅读产品契约，理解本次需求的业务目标、业务规则、业务流程及验收标准。

识别每项业务需求对应的前端技术实现要求，包括页面展示、用户交互、数据获取及状态变化。

### 3.2 分析现有代码

结合项目上下文，阅读与本次需求相关的前端实际代码，重点分析：

- 页面结构及组件组织方式。
- 路由配置及导航逻辑。
- 状态管理方案（全局状态、局部状态及持久化策略）。
- 接口调用封装及请求响应处理方式。
- 表单处理及校验方式。
- 公共组件、工具函数及样式规范。
- 现有实现方式与编码规范。

不得仅根据项目文档推断代码实现，必须通过实际代码确认。

### 3.3 确定技术方案

根据业务需求、后端接口文档及现有代码，分析：

- 需要新增、修改的页面及组件。
- 各页面及组件承担的职责及相互关系。
- 路由及页面跳转逻辑是否需要调整。
- 状态管理方案是否需要变更。
- 需要调用的后端接口及数据处理方式。
- 表单字段、校验规则及错误提示方式。
- 是否能够复用已有组件及公共能力。
- 是否需要引入新的第三方依赖或组件库。

对于存在多种可行方案的关键技术决策，允许提出推荐方案和备选方案，说明各方案的优缺点及影响，由开发者确认后再写入正式契约。

技术设计细化程度根据需求复杂度灵活决定。简单需求可以描述到页面级，复杂需求应明确具体组件、关键函数及其职责。

## 四、契约编写

前端技术契约分为最小必要集和可选扩展集，提供的是维度参考而非封闭清单。AI应根据需求实际上下文进行推理判断，避免机械套用。

### 4.0 章节结构推断

在编写具体内容前，先分析前端方案特征并确定章节结构：

1. **方案特征提取**：从产品契约和代码分析中提取关键特征标签（如涉及权限控制、复杂数据展示、新依赖引入、多端适配、复杂交互或状态管理等）。
2. **最小必要集保底**：以下核心维度必须全部覆盖——技术方案概述、页面与组件结构、路由与导航、交互逻辑、状态管理、接口调用、表单与校验、技术约束。
3. **可选扩展集筛选**：根据特征标签正向选取相关扩展维度（权限控制、数据展示规则、第三方组件与库、响应式适配、代码示例），反向排除明显无关的维度。
4. **缺口识别**：检查前端方案的每个重要方面是否都有章节承载，如发现「无章节可归」的重要内容，必须主动新增章节并说明理由。
5. **精简校验**：确认无冗余章节，确保契约厚度与需求复杂度匹配。

输出计划编写的章节清单（格式：「章节名 → 选取理由」），确认后开始正式编写。

优先完成最小必要集，根据需求实际情况补充可选扩展内容。

### 4.1 最小必要集

#### 1. 技术方案概述

说明整体前端实现思路、涉及的页面与组件及核心处理流程。

#### 2. 页面与组件结构

列出新增或变更的页面及组件，明确各组件的职责、相互关系及数据传递方式。

必要时明确具体文件路径及关键组件职责。

#### 3. 路由与导航

明确新增或变更的路由、页面跳转逻辑及参数传递方式。

#### 4. 交互逻辑

描述用户点击、输入、提交等操作对应的前端处理逻辑及状态变化。

#### 5. 状态管理

明确涉及的全局状态、局部状态、状态流转及持久化策略。

#### 6. 接口调用

列出本次需求涉及的后端接口，明确以下内容：

- 请求参数组装方式。
- 响应数据处理逻辑。
- 异常处理方式。
- 错误码对应的页面反馈策略。

接口调用设计必须与后端接口文档保持一致，不得擅自变更接口路径、请求方法、参数结构或响应格式。如果发现后端接口文档存在遗漏或错误，必须暂停并反馈给开发者确认。

#### 7. 表单与校验

明确表单字段、校验规则及错误提示方式。

#### 8. 技术约束

明确本次开发必须遵循的前端框架规范（如组合式 API 风格）、组件使用约束、样式规范及其他技术限制。

### 4.2 可选扩展集

根据需求实际情况选择性补充：

1. 权限控制：页面级、按钮级的权限判断逻辑，以及无权限时的展示策略。
2. 数据展示规则：列表排序、分页、空状态、加载状态及数据格式化规则。
3. 第三方组件与库：引入的外部组件或依赖库、使用方式及版本要求。
4. 响应式适配：不同屏幕尺寸下的页面布局、组件展示及交互差异。
5. 代码示例：对复杂交互或状态管理提供参考代码。

不涉及的内容无需强行补充。

## 五、文档管理

### 5.1 固定目录

前端技术契约与产品契约放在同一个需求版本目录下：

```text
交付契约/
└── 需求名称/
    └── v1/
        ├── 1.产品契约.md
        └── 2.前端技术契约.md
```

### 5.2 版本管理

1. 新需求使用对应的v1目录。
2. 已有需求迭代时使用开发者指定的新版本目录。
3. 历史版本必须保留，不得直接覆盖。
4. 新版本必须生成完整的前端技术契约，不能只记录本次变更内容。

## 六、审核与迭代

技术契约初稿完成后，必须经过审核。

### 6.1 AI自检

检查：

- 技术方案是否覆盖产品契约中的业务需求。
- 页面与组件结构是否明确。
- 路由与导航设计是否完整。
- 交互逻辑是否覆盖正常和异常场景。
- 接口调用是否与后端接口文档一致。
- 状态管理及表单校验是否合理。
- 是否符合项目现有架构及编码规范。
- 是否存在未经确认的技术决策。
- 是否存在不必要的技术设计。

### 6.2 开发者审核

向开发者展示技术契约初稿及待确认事项，收集修改意见。

对于关键技术方案，必须由开发者确认后才能定稿。

### 6.3 一致性检查

每次修改完成后，必须重新检查：

1. 技术方案是否符合产品契约。
2. 每项技术设计是否能够追溯到具体业务需求。
3. 页面与组件结构是否符合项目架构设计。
4. 接口调用是否与后端接口文档保持一致。
5. 路由、状态管理及交互设计是否相互一致。
6. 是否符合项目编码规范。
7. 是否与现有代码实现冲突。
8. 是否存在未经确认的技术约定。

发现冲突或无法确认的内容时，主动向开发者反馈，不得自行决定。

重复执行修改、检查和审核，直到开发者确认定稿。

## 七、执行约束

1. 必须以产品契约、后端接口文档和项目上下文作为技术设计依据。
2. 不得擅自修改产品契约中的业务规则。
3. 不得脱离实际代码设计与项目架构无关的实现方案。
4. 不得擅自引入新的技术栈、第三方依赖或公共组件。
5. 不得将未经确认的技术建议写入正式契约。
6. 每项技术设计必须能够追溯到对应的业务需求。
7. 不得擅自修改业务代码、产品契约、后端技术契约及其他非目标文档。
8. 不得覆盖历史版本技术契约。
9. 接口调用设计必须与后端接口文档保持一致，不得擅自变更。
10. 发现后端接口文档遗漏或错误时，必须暂停并反馈，不得自行假设或调整。
11. 未经开发者确认，不得宣称技术契约已经定稿。

## 八、完成标准

同时满足以下条件，才算完成：

- [ ] 已读取项目根目录下的「项目上下文.md」、产品契约及后端接口文档。
- [ ] 已完成相关前端代码分析。
- [ ] 已明确本次需求的前端技术实现方案。
- [ ] 已完成最小必要集。
- [ ] 必要的可选扩展内容已补充。
- [ ] 每项技术设计均可追溯到产品契约。
- [ ] 接口调用设计与后端接口文档保持一致。
- [ ] 技术契约已存放在规定目录。
- [ ] 已完成AI自检及一致性检查。
- [ ] 开发者已审核并确认定稿。

完成后，向开发者说明技术契约的存放位置、涉及的核心页面及组件、主要技术变更及与后端接口的对应关系。
