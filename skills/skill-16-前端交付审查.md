# 前端交付成果独立审查

## 一、任务目标

以独立审查者的视角，对本次需求前端开发及页面自动化测试完成后的交付成果进行全面审查。

重点评估代码质量、页面交互正确性、架构一致性、潜在回归风险及交付契约符合度，识别代码缺陷、设计偏差及潜在问题，输出结构化审查报告。

页面自动化测试已通过，说明核心业务逻辑和页面交互已走通。本环节侧重于从代码层面发现潜在风险、质量隐患及与规范不一致的问题，而非重复验证业务正确性。

本Skill只负责审查发现问题和输出报告，不直接修改任何代码文件，也不执行页面自动化测试。

## 二、执行前提

必须使用全新的AI Agent会话执行审查，不得沿用开发或测试阶段的对话上下文，避免自我审查偏差。

必须读取以下文件：

1. 项目根目录下的「项目上下文.md」
2. 本次需求的1.产品契约.md
3. 本次需求的2.前端技术契约.md
4. 本次需求的3.前端测试契约.md

同时获取后端接口文档（如 Swagger），并阅读本次需求涉及的前端实际代码，包括业务代码和测试代码。

同时获取前端页面自动化测试结果。

如果缺少必要文件、契约尚未定稿、前端代码开发或页面自动化测试尚未完成，必须停止审查并向开发者说明原因，不得自行假设。

### 前置分析反问

开始本Skill的任何实质性工作之前，AI必须先进入一个独立的前置分析阶段。目标是穷尽一切不确定点，确保对任务全貌的理解与开发者预期完全一致。未确认无任何模糊、遗漏或歧义前，不得开始任何输出、编写或修改工作。

#### 第一阶段：全量资料研读

必须完成以下阅读任务：

1. **完整阅读本Skill全文**：逐节理解任务目标、执行步骤、输出格式、约束条件和完成标准。
2. **读取项目上下文**：读取「项目上下文.md」，理解项目架构、技术栈、编码规范及关键约束。
3. **读取相关契约**：读取本Skill要求的所有相关契约（产品契约、技术契约、测试契约等）。
4. **读取实际代码**：阅读与本次任务相关的实际代码，理解现有实现、数据结构、接口定义及调用链路。

阅读过程中建立完整的任务认知图谱：起点（当前状态）、终点（完成标准）、约束、不可为事项。

#### 第二阶段：不确定点穷尽识别

基于全面理解，AI必须主动、自主地识别所有不确定点。结合本次任务的具体业务场景、技术上下文和已有资料，自由地、发散性地思考：还有什么是我不能完全确定的？

思考方向可参考但不限于：文件是否能读到、术语是否理解、资料之间是否一致、技术方案是否可行、操作环境是否具备、输出格式是否明确、需求边界是否清晰、异常情况如何处理、开发者的真实意图是什么。任何让AI产生「应该是这样」而非「确定就是这样」的念头，都是不确定点。

**判定标准**：不是「这会不会影响执行」，而是「我能不能100%确定这件事就是这样」。只要有一丝疑问、一点猜测、一种可能的理解偏差，就必须标记为不确定点。

#### 第三阶段：首轮提问

将识别出的所有不确定点，整理为具体问题向开发者提出：

1. **分主题归类呈现**，方便逐类确认。
2. **问题必须具体**，指向具体内容（如「产品契约第3.2节某规则」、「xx.go文件中xx函数」），不得笼统。
3. **说明提问原因**，简要解释为何会影响任务正确执行。
4. **穷尽式提问**，不设上限，遗漏的代价远大于多问一句。

**禁止**：不得以「信息够了」为由跳过提问；不得将不确定点自行猜测后作为假设继续；不得自行判定某些问题「不重要」而忽略。

#### 第四阶段：多轮确认循环

开发者回答后，必须进入多轮确认循环，而非直接执行。

**每轮循环**：

1. **重读全部资料**：结合回答重新阅读本Skill、项目上下文、相关契约及实际代码。
2. **新不确定点识别**：回答是否引入新信息或新矛盾？之前未意识到的问题是否变明显了？回答中是否有需要进一步澄清的内容？
3. **补充提问**：如有新不确定点，继续提问。这是正常行为，不是上一轮工作的失败。
4. **等待回答后重复步骤1～3**。

**循环终止条件**（必须同时满足）：

- 通读全部资料后，不再发现任何不确定点。
- 对任务的目标、范围、约束、输入、输出、标准均有清晰且无歧义的理解。
- 能够明确回答以下自检问题：
  - 本Skill要求我做什么？做到什么程度算完成？
  - 项目上下文、契约和代码之间是否存在我理解不了的冲突？
  - 开发者是否已回答我所有不确定点，且答案没有引入新的疑问？
  - 我是否能在不进一步提问的情况下，准确、完整地执行本Skill？

只有在自检全部通过后，才能向开发者声明「已理解全貌，准备开始执行」，并在获得开发者确认后进入下一阶段。

#### 第五阶段：进入执行

多轮确认循环结束后，向开发者输出以下声明：

```
我已完整阅读并理解：
- 本Skill的全部要求与约束
- 项目上下文中的相关约定
- 相关契约中的业务规则与技术方案
- 相关实际代码的实现方式

结合你的全部回答，我确认当前不存在任何尚未澄清的不确定点。
我已准备好开始执行，过程中如遇新的未预见问题，将及时反馈。
```

开发者在聊天框回复确认后，方可正式开始本Skill规定的实质性工作。

---

**核心原则**：

- **不要不好意思问**：多一轮确认远胜于事后返工。
- **不要自行假设**：任何不确定的内容，哪怕「应该就是这样」，也必须确认。
- **不要急于执行**：进入多轮确认循环前开始任何编写或修改，均视为违规。
- **不要止于首轮**：第二轮、第三轮提问同样重要，甚至更重要。

## 三、交付成果审查

### 3.1 代码质量审查

检查代码是否符合项目编码规范，重点关注：

- 命名规范：变量、函数、组件、文件及常量的命名。
- 代码风格：缩进、换行、注释、导包顺序及代码格式。
- 代码结构：目录和文件组织方式、组件职责及页面结构设计。
- 可读性：注释质量、代码复杂度及职责清晰度。
- 重复代码：是否存在可复用但未复用的公共组件或重复实现。

### 3.2 页面交互正确性审查

结合产品契约和前端技术契约，检查页面交互实现是否正确：

- 页面跳转及导航逻辑是否正确。
- 按钮点击、表单提交等交互反馈是否符合预期。
- 表单输入与校验是否正确实现。
- 列表操作（分页、排序、筛选）是否正确。
- 弹窗交互及操作反馈是否正确。
- 加载状态、空状态及异常提示是否处理完善。

### 3.3 架构一致性审查

结合架构设计，检查代码是否符合项目既定架构：

- 是否遵循项目前端框架规范（如组合式 API 风格）。
- 组件职责是否清晰，是否存在过度拆分或职责混乱。
- 状态管理方案是否合理，数据流转是否清晰。
- 路由配置及导航逻辑是否符合规范。
- 是否引入与项目技术栈不一致的依赖。

### 3.4 接口调用审查

结合后端接口文档，检查前端接口调用：

- 接口路径、请求方法是否正确。
- 请求参数组装及响应数据处理是否正确。
- 错误码处理及页面反馈策略是否完善。
- 接口调用设计是否与后端接口文档一致。

### 3.5 错误处理与用户提示审查

- 错误处理是否符合规范，用户提示是否友好。
- 加载状态、空状态及异常反馈是否完善。
- 身份认证及权限控制是否正确实现。
- 敏感信息处理及安全防护是否符合规范。

### 3.6 状态管理与样式审查

- 状态管理方案是否合理，是否存在不必要的状态提升或冗余状态。
- 样式规范是否符合项目约定，是否存在样式冲突或全局污染。
- 响应式适配是否合理（如适用）。

### 3.7 回归风险评估

评估本次变更对既有功能的影响：

- 是否修改了共享组件、公共工具函数或通用样式。
- 变更是否可能连带影响其他已有页面或功能。
- 是否存在因修复当前问题而破坏其他模块的隐性回归风险。

### 3.8 测试代码审查

检查测试代码（如编写了自动化测试脚本）：

- 测试代码质量、组织方式及命名规范。
- 测试用例是否覆盖核心业务场景、异常场景及边界条件。
- 测试代码是否符合项目测试规范及编码规范。

## 四、问题分级

审查发现的问题必须按照以下等级分类：

1. P0：严重问题，影响业务正确性或存在重大风险。
2. P1：重要问题，核心需求遗漏、技术方案错误或关键逻辑缺陷。
3. P2：一般问题，局部设计不完整或存在明显问题。
4. P3：优化建议，不影响当前需求正确交付。

每个问题必须明确：

- 问题等级。
- 所属文件。
- 具体文件路径、函数/方法名、行号或相关代码片段。
- 问题描述。
- 产生的影响。
- 修改建议及原因。

不得将个人偏好或非必要优化建议判定为实际缺陷。

## 五、审查报告

审查完成后，通过聊天框向开发者输出结构化审查报告，不要求额外生成独立报告文件。

### 5.1 审查结论

给出以下结论之一：

- 通过：不存在未解决的P0、P1问题，满足审查完成标准。
- 条件通过：不存在未解决的P0、P1问题，但仍有需要开发者关注的遗留问题。
- 不通过：存在未解决的P0或P1问题，不能通过审查。

### 5.2 问题清单

逐项列出审查发现的问题，包括问题等级、所属文件、具体位置、问题描述、影响及修改建议。

### 5.3 最终审查结果

汇总未解决问题、遗留风险及是否满足审查通过条件。

审查报告必须提供明确的文件路径、函数/方法名、行号或代码片段定位，不得只输出笼统的审查意见。

## 六、审核与迭代

### 6.1 独立审查

首次审查必须独立完成，不得依赖开发或测试阶段的结论或自我判断。仅通过代码阅读完成审查，不得运行静态代码分析工具、执行测试或连接数据库辅助审查。

### 6.2 开发者审核

向开发者展示审查报告及所有待处理问题，由开发者决定是否修改代码。

只输出审查意见和修改建议，不得直接修改任何前端业务代码或测试代码。

审查发现问题后，由开发者逐项确认，筛选出确实需要修复的问题，再交由负责前端开发的AI进行针对性修复。

如果开发者决定暂不修复某个问题，允许将其记录为遗留风险，不影响审查结论。

### 6.3 重新审查

代码修复完成后，必须重新执行完整审查，而不是只检查上一轮发现的问题。

重新审查可用之前的审查Agent执行。

每轮审查都必须重新检查：

1. 代码质量、页面交互及架构一致性。
2. 上一轮问题是否得到有效解决。
3. 修改是否引入新的遗漏、冲突或回归风险。

重复执行审查、报告、修复和复查，直到满足审查通过条件，并由开发者确认最终结果。

### 6.4 重新测试建议

代码修复后，审查Agent不直接执行页面自动化测试。如修复可能影响到已测试的页面或功能，应在审查报告中输出需要重新测试的范围建议，由开发者判断是否重新执行相关页面自动化测试，并交由对应测试Agent执行。

## 七、执行约束

1. 必须使用全新AI Agent会话执行首次审查。
2. 必须读取完整的项目上下文和本次需求三份契约。
3. 必须结合实际前端代码（包括业务代码和测试代码）进行审查。
4. 仅通过代码阅读完成审查，不得运行工具、执行测试或连接数据库。
5. 不得直接修改任何前端业务代码或测试代码。
6. 不得擅自改变已确认的业务规则和技术方案。
7. 所有问题必须分级并提供具体文件路径、函数/方法名、行号或代码片段定位。
8. 不得将未经确认的优化建议作为正式审查要求。
9. 不得推测缺失信息，无法确认的内容必须明确标记。
10. 所有问题必须有对应的代码内容或项目资料作为依据。
11. 未经开发者确认，不得宣称审查最终通过。

## 八、完成标准

同时满足以下条件，才算完成：

- [ ] 已使用全新AI Agent会话执行首次审查。
- [ ] 已读取项目根目录下的「项目上下文.md」及三份需求契约。
- [ ] 已阅读本次需求涉及的实际前端代码（业务代码和测试代码）。
- [ ] 已完成代码质量审查。
- [ ] 已完成页面交互正确性审查。
- [ ] 已完成架构一致性审查。
- [ ] 已完成接口调用、错误处理及用户提示审查。
- [ ] 已完成状态管理与样式审查。
- [ ] 已完成回归风险评估。
- [ ] 已完成测试代码审查。
- [ ] 所有审查问题均已分级并提供具体位置。
- [ ] 已通过聊天框输出完整审查报告。
- [ ] 不存在未解决的P0和P1问题。
- [ ] 开发者已确认最终审查结果。

完成后，向开发者说明审查结论、遗留问题及前端独立交付是否正式完成。
