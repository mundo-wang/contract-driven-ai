# 需求沟通与等级判定

## 一、任务目标

与开发者充分沟通业务需求，理解需求背景、目标及范围，分析需求规模和复杂度，判定需求等级（L1/L2/L3），并给出等级判定依据。

## 二、执行前提

### 前置分析反问

开始执行前，AI必须先完成以下步骤：

1. **资料分析**：仔细阅读本Skill要求读取的全部资料，包括项目上下文、相关契约及实际代码，全面理解本次任务的范围、目标和约束。
2. **识别不确定点**：基于资料分析，主动识别以下类型的问题：
   - 资料之间存在矛盾、冲突或不一致的地方。
   - 契约、代码或文档中存在模糊、遗漏或无法确认的内容。
   - 本Skill的流程、标准或要求与当前项目实际情况可能存在不匹配的地方。
   - 开发者可能尚未明确说明，但对本次任务执行有实质性影响的约束、例外或特殊要求。
3. **列举并提问**：将识别出的不确定点整理为具体问题，向开发者提问。提问应聚焦影响任务正确性的关键问题，避免重复询问已经明确的信息。
4. **确认后执行**：开发者解答后，AI以解答为准开展后续工作。如经分析后不存在不确定点，可直接开始执行。

## 三、需求沟通

### 3.1 接收需求输入

开发者应提供以下信息：

- 需求背景与业务目标。
- 功能范围及操作场景。
- 用户角色及权限关系。
- 交互说明（如有原型图、设计稿、流程图等图片资料，应一并上传）。
- 已知的业务规则、约束条件及边界。
- 时间要求或其他特殊约束。

AI应仔细阅读并理解所有输入内容，不得遗漏或忽略开发者明确提供的信息。如信息不完整，允许AI主动向开发者索要缺失内容。

### 3.2 主动反问

基于对需求的初步理解，AI应主动识别以下类型的问题并向开发者提问：

- 需求描述中不明确或存在歧义的地方。
- 开发者可能忽略的业务规则或隐含约束。
- 边界条件、异常场景及极端情况。
- 与现有业务可能存在的冲突或影响。
- 权限、数据、安全等方面的约束。

提问应聚焦业务层面（"做什么"），不涉及技术实现层面（"怎么做"）。

### 3.3 多轮沟通确认

允许多轮反问与补充：

- 开发者回答后，AI应继续分析是否还有未明确的问题。
- 如开发者补充了新内容，AI应重新评估是否已充分理解。
- 直到AI确认已理解全部需求内容，不存在误解或遗漏。

如沟通过程中开发者修改或补充了需求，应重新评估需求等级。

### 3.4 需求理解确认

沟通结束后，AI应向开发者确认以下内容的理解是否准确：

- 需求背景与业务目标。
- 核心功能及操作场景。
- 关键业务规则及约束。
- 边界条件及异常场景。
- 需求等级判定结果及依据。

## 四、等级判定

### 4.1 等级划分标准

以以下定义为基准，结合实际情况灵活判断：

**L1（简单需求）**

- 修改范围较小，业务逻辑明确。
- 不涉及复杂数据结构或架构变更。
- 风险较低且验收标准清晰。
- 示例：单表CRUD、简单页面调整、字段增删。

**L2（普通需求）**

- 涉及多个模块或较完整的业务逻辑。
- 存在一定的技术设计与业务规则。
- 会涉及数据库、接口或模块间协作。
- 需要较完整的测试与验收。

**L3（复杂需求）**

- 涉及核心业务流程或多个子系统。
- 重大架构调整或复杂数据结构变更。
- 具有较高的业务或技术风险。
- 需求范围较大、难以一次性完成开发与验证。

### 4.2 需求等级判定

根据沟通确认后的需求内容，综合以下维度进行判定：

- 业务复杂度：涉及的业务规则数量及逻辑复杂程度。
- 影响范围：涉及的模块、页面、接口数量。
- 数据变更：是否涉及数据库结构变更或大量数据迁移。
- 架构影响：是否涉及架构调整或公共组件变更。
- 风险程度：业务风险、技术风险及回滚难度。

### 4.3 判定结果输出

输出内容应包括：

- 判定等级（L1/L2/L3）。
- 判定依据（基于哪些维度得出此结论）。
- 关键风险提示（如适用）。

如判定为L3，应给出需求拆分建议，说明建议拆分为几个子需求及各子需求的交付目标。

## 五、输出与流程选择

### 5.1 等级确认

等级判定结果由AI提出建议，最终由开发者确认。如开发者不同意AI的判定，以开发者意见为准。

### 5.2 流程选择

开发者确认等级后，自行决定后续流程：

- **L1级**：执行轻量级交付流程。
- **L2/L3级**：进入常规交付流程，开始编写产品契约。

本Skill的输出结果（已确认的需求理解）直接作为后续Skill的输入，无需额外落地文档。

## 六、执行约束

1. 必须充分理解开发者提供的全部需求信息，不得遗漏。
2. 提问必须聚焦业务层面，不涉及技术实现方案。
3. 必须给予AI充分的反问机会，直到需求细节充分明确。
4. 多轮沟通中如需求发生变更，必须重新评估等级。
5. 等级判定必须有明确依据，不得凭空猜测。
6. 判定结果由开发者最终确认，以开发者意见为准。
7. 不编写正式的产品契约，产品契约编写由后续环节负责。
8. 输出结果直接通过聊天框反馈，不要求生成独立文档。

## 七、完成标准

同时满足以下条件，才算完成：

- [ ] 已接收并理解开发者提供的全部需求信息。
- [ ] 已完成主动反问，需求细节已充分明确。
- [ ] 已向开发者确认需求理解无误。
- [ ] 已根据需求内容判定等级并给出依据。
- [ ] 如判定为L3，已给出需求拆分建议。
- [ ] 等级判定结果已由开发者确认。
- [ ] 开发者已明确选择后续交付流程（轻量级交付或常规交付）。
- [ ] 未擅自编写产品契约或其他非本Skill职责的文档。

完成后，向开发者说明需求理解摘要、等级判定结果及建议的后续流程。
