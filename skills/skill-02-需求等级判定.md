# 需求沟通与等级判定

## 一、任务目标

与开发者充分沟通业务需求，理解需求背景、目标及范围，分析需求规模和复杂度，判定需求等级（L1/L2/L3），并给出等级判定依据。

## 二、执行前提

### 前置分析反问

开始本Skill的任何实质性工作之前，AI必须先进入一个独立的前置分析阶段。目标是穷尽一切不确定点，确保对任务全貌的理解与开发者预期完全一致。未确认无任何模糊、遗漏或歧义前，不得开始任何输出、编写或修改工作。

#### 第一阶段：全量资料研读

必须完成以下阅读任务：

1. **完整阅读本Skill全文**：逐节理解任务目标、执行步骤、输出格式、约束条件和完成标准。
2. **读取项目上下文**：读取「项目上下文.md」，理解项目架构、技术栈、编码规范及关键约束。
3. **读取相关契约**：读取本Skill要求的所有相关契约（产品契约、技术契约、测试契约等）。
4. **读取实际代码**：阅读与本次任务相关的实际代码，理解现有实现、数据结构、接口定义及调用链路。

阅读过程中建立完整的任务认知图谱：起点（当前状态）、终点（完成标准）、约束、不可为事项。

#### 第二阶段：不确定点穷尽识别

基于全面理解，AI必须主动、自主地识别所有不确定点。结合本次任务的具体业务场景、技术上下文和已有资料，自由地、发散性地思考：还有什么是我不能完全确定的？

思考方向可参考但不限于：文件是否能读到、术语是否理解、资料之间是否一致、技术方案是否可行、操作环境是否具备、输出格式是否明确、需求边界是否清晰、异常情况如何处理、开发者的真实意图是什么。任何让AI产生「应该是这样」而非「确定就是这样」的念头，都是不确定点。

**判定标准**：不是「这会不会影响执行」，而是「我能不能100%确定这件事就是这样」。只要有一丝疑问、一点猜测、一种可能的理解偏差，就必须标记为不确定点。

#### 第三阶段：首轮提问

将识别出的所有不确定点，整理为具体问题向开发者提出：

1. **分主题归类呈现**，方便逐类确认。
2. **问题必须具体**，指向具体内容（如「产品契约第3.2节某规则」、「xx.go文件中xx函数」），不得笼统。
3. **说明提问原因**，简要解释为何会影响任务正确执行。
4. **穷尽式提问**，不设上限，遗漏的代价远大于多问一句。

**禁止**：不得以「信息够了」为由跳过提问；不得将不确定点自行猜测后作为假设继续；不得自行判定某些问题「不重要」而忽略。

#### 第四阶段：多轮确认循环

开发者回答后，必须进入多轮确认循环，而非直接执行。

**每轮循环**：

1. **重读全部资料**：结合回答重新阅读本Skill、项目上下文、相关契约及实际代码。
2. **新不确定点识别**：回答是否引入新信息或新矛盾？之前未意识到的问题是否变明显了？回答中是否有需要进一步澄清的内容？
3. **补充提问**：如有新不确定点，继续提问。这是正常行为，不是上一轮工作的失败。
4. **等待回答后重复步骤1～3**。

**循环终止条件**（必须同时满足）：

- 通读全部资料后，不再发现任何不确定点。
- 对任务的目标、范围、约束、输入、输出、标准均有清晰且无歧义的理解。
- 能够明确回答以下自检问题：
  - 本Skill要求我做什么？做到什么程度算完成？
  - 项目上下文、契约和代码之间是否存在我理解不了的冲突？
  - 开发者是否已回答我所有不确定点，且答案没有引入新的疑问？
  - 我是否能在不进一步提问的情况下，准确、完整地执行本Skill？

只有在自检全部通过后，才能向开发者声明「已理解全貌，准备开始执行」，并在获得开发者确认后进入下一阶段。

#### 第五阶段：进入执行

多轮确认循环结束后，向开发者输出以下声明：

```
我已完整阅读并理解：
- 本Skill的全部要求与约束
- 项目上下文中的相关约定
- 相关契约中的业务规则与技术方案
- 相关实际代码的实现方式

结合你的全部回答，我确认当前不存在任何尚未澄清的不确定点。
我已准备好开始执行，过程中如遇新的未预见问题，将及时反馈。
```

开发者在聊天框回复确认后，方可正式开始本Skill规定的实质性工作。

---

**核心原则**：

- **不要不好意思问**：多一轮确认远胜于事后返工。
- **不要自行假设**：任何不确定的内容，哪怕「应该就是这样」，也必须确认。
- **不要急于执行**：进入多轮确认循环前开始任何编写或修改，均视为违规。
- **不要止于首轮**：第二轮、第三轮提问同样重要，甚至更重要。

## 三、需求沟通

### 3.1 接收需求输入

开发者应提供以下信息：

- 需求背景与业务目标。
- 功能范围及操作场景。
- 用户角色及权限关系。
- 交互说明（如有原型图、设计稿、流程图等图片资料，应一并上传）。
- 已知的业务规则、约束条件及边界。
- 时间要求或其他特殊约束。

AI应仔细阅读并理解所有输入内容，不得遗漏或忽略开发者明确提供的信息。如信息不完整，允许AI主动向开发者索要缺失内容。

### 3.2 主动反问

基于对需求的初步理解，AI应主动识别以下类型的问题并向开发者提问：

- 需求描述中不明确或存在歧义的地方。
- 开发者可能忽略的业务规则或隐含约束。
- 边界条件、异常场景及极端情况。
- 与现有业务可能存在的冲突或影响。
- 权限、数据、安全等方面的约束。

提问应聚焦业务层面（「做什么」），不涉及技术实现层面（「怎么做」）。

### 3.3 多轮沟通确认

允许多轮反问与补充：

- 开发者回答后，AI应继续分析是否还有未明确的问题。
- 如开发者补充了新内容，AI应重新评估是否已充分理解。
- 直到AI确认已理解全部需求内容，不存在误解或遗漏。

如沟通过程中开发者修改或补充了需求，应重新评估需求等级。

### 3.4 需求理解确认

沟通结束后，AI应向开发者确认以下内容的理解是否准确：

- 需求背景与业务目标。
- 核心功能及操作场景。
- 关键业务规则及约束。
- 边界条件及异常场景。
- 需求等级判定结果及依据。

## 四、等级判定

### 4.1 等级划分标准

以以下定义为基准，结合实际情况灵活判断：

**L1（简单需求）**

- 修改范围较小，业务逻辑明确。
- 不涉及复杂数据结构或架构变更。
- 风险较低且验收标准清晰。
- 示例：单表CRUD、简单页面调整、字段增删。

**L2（普通需求）**

- 涉及多个模块或较完整的业务逻辑。
- 存在一定的技术设计与业务规则。
- 会涉及数据库、接口或模块间协作。
- 需要较完整的测试与验收。

**L3（复杂需求）**

- 涉及核心业务流程或多个子系统。
- 重大架构调整或复杂数据结构变更。
- 具有较高的业务或技术风险。
- 需求范围较大、难以一次性完成开发与验证。

### 4.2 需求等级判定

根据沟通确认后的需求内容，综合以下维度进行判定：

- 业务复杂度：涉及的业务规则数量及逻辑复杂程度。
- 影响范围：涉及的模块、页面、接口数量。
- 数据变更：是否涉及数据库结构变更或大量数据迁移。
- 架构影响：是否涉及架构调整或公共组件变更。
- 风险程度：业务风险、技术风险及回滚难度。

### 4.3 判定结果输出

输出内容应包括：

- 判定等级（L1/L2/L3）。
- 判定依据（基于哪些维度得出此结论）。
- 关键风险提示（如适用）。

如判定为L3，应给出需求拆分建议，说明建议拆分为几个子需求及各子需求的交付目标。

## 五、输出与流程选择

### 5.1 等级确认

等级判定结果由AI提出建议，最终由开发者确认。如开发者不同意AI的判定，以开发者意见为准。

### 5.2 流程选择

开发者确认等级后，自行决定后续流程：

- **L1级**：执行轻量级交付流程。
- **L2/L3级**：进入常规交付流程，开始编写产品契约。

本Skill的输出结果（已确认的需求理解）直接作为后续Skill的输入，无需额外落地文档。

## 六、执行约束

1. 必须充分理解开发者提供的全部需求信息，不得遗漏。
2. 提问必须聚焦业务层面，不涉及技术实现方案。
3. 必须给予AI充分的反问机会，直到需求细节充分明确。
4. 多轮沟通中如需求发生变更，必须重新评估等级。
5. 等级判定必须有明确依据，不得凭空猜测。
6. 判定结果由开发者最终确认，以开发者意见为准。
7. 不编写正式的产品契约，产品契约编写由后续环节负责。
8. 输出结果直接通过聊天框反馈，不要求生成独立文档。

## 七、完成标准

同时满足以下条件，才算完成：

- [ ] 已接收并理解开发者提供的全部需求信息。
- [ ] 已完成主动反问，需求细节已充分明确。
- [ ] 已向开发者确认需求理解无误。
- [ ] 已根据需求内容判定等级并给出依据。
- [ ] 如判定为L3，已给出需求拆分建议。
- [ ] 等级判定结果已由开发者确认。
- [ ] 开发者已明确选择后续交付流程（轻量级交付或常规交付）。
- [ ] 未擅自编写产品契约或其他非本Skill职责的文档。

完成后，向开发者说明需求理解摘要、等级判定结果及建议的后续流程。
