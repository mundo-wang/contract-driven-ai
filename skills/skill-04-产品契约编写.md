# 产品契约编写

## 一、任务目标

将已确认的需求结构化地编写为正式产品契约，作为前后端共同遵循的业务基准。

产品契约描述系统需要实现什么业务能力，不涉及具体技术实现方案。

遵循最小必要集优先原则，仅在业务确实需要时补充可选扩展内容，避免过度设计。

## 二、执行前提

1. 当前工作环境必须是具备本地项目文件读取和修改能力的AI Agent。
2. 需求已在前一阶段充分沟通并确认，不存在未解决的歧义。
3. 必须先读取项目根目录下的「项目上下文.md」，了解项目背景、业务模块及关键术语。
4. 开发者必须明确本次需求属于新需求还是已有需求迭代。
5. 如果属于已有需求迭代，开发者必须告知需要读取的历史产品契约，AI应先读取并理解相关内容。
6. 不得擅自修改历史版本的产品契约。

如果缺少必要信息，主动向开发者提问，不得直接编造需求。

### 前置分析反问

开始本Skill的任何实质性工作之前，AI必须先进入一个独立的前置分析阶段。目标是穷尽一切不确定点，确保对任务全貌的理解与开发者预期完全一致。未确认无任何模糊、遗漏或歧义前，不得开始任何输出、编写或修改工作。

#### 第一阶段：全量资料研读

必须完成以下阅读任务：

1. **完整阅读本Skill全文**：逐节理解任务目标、执行步骤、输出格式、约束条件和完成标准。
2. **读取项目上下文**：读取「项目上下文.md」，理解项目架构、技术栈、编码规范及关键约束。
3. **读取相关契约**：读取本Skill要求的所有相关契约（产品契约、技术契约、测试契约等）。
4. **读取实际代码**：阅读与本次任务相关的实际代码，理解现有实现、数据结构、接口定义及调用链路。

阅读过程中建立完整的任务认知图谱：起点（当前状态）、终点（完成标准）、约束、不可为事项。

#### 第二阶段：不确定点穷尽识别

基于全面理解，AI必须主动、自主地识别所有不确定点。结合本次任务的具体业务场景、技术上下文和已有资料，自由地、发散性地思考：还有什么是我不能完全确定的？

思考方向可参考但不限于：文件是否能读到、术语是否理解、资料之间是否一致、技术方案是否可行、操作环境是否具备、输出格式是否明确、需求边界是否清晰、异常情况如何处理、开发者的真实意图是什么。任何让AI产生「应该是这样」而非「确定就是这样」的念头，都是不确定点。

**判定标准**：不是「这会不会影响执行」，而是「我能不能100%确定这件事就是这样」。只要有一丝疑问、一点猜测、一种可能的理解偏差，就必须标记为不确定点。

#### 第三阶段：首轮提问

将识别出的所有不确定点，整理为具体问题向开发者提出：

1. **分主题归类呈现**，方便逐类确认。
2. **问题必须具体**，指向具体内容（如「产品契约第3.2节某规则」、「xx.go文件中xx函数」），不得笼统。
3. **说明提问原因**，简要解释为何会影响任务正确执行。
4. **穷尽式提问**，不设上限，遗漏的代价远大于多问一句。

**禁止**：不得以「信息够了」为由跳过提问；不得将不确定点自行猜测后作为假设继续；不得自行判定某些问题「不重要」而忽略。

#### 第四阶段：多轮确认循环

开发者回答后，必须进入多轮确认循环，而非直接执行。

**每轮循环**：

1. **重读全部资料**：结合回答重新阅读本Skill、项目上下文、相关契约及实际代码。
2. **新不确定点识别**：回答是否引入新信息或新矛盾？之前未意识到的问题是否变明显了？回答中是否有需要进一步澄清的内容？
3. **补充提问**：如有新不确定点，继续提问。这是正常行为，不是上一轮工作的失败。
4. **等待回答后重复步骤1～3**。

**循环终止条件**（必须同时满足）：

- 通读全部资料后，不再发现任何不确定点。
- 对任务的目标、范围、约束、输入、输出、标准均有清晰且无歧义的理解。
- 能够明确回答以下自检问题：
  - 本Skill要求我做什么？做到什么程度算完成？
  - 项目上下文、契约和代码之间是否存在我理解不了的冲突？
  - 开发者是否已回答我所有不确定点，且答案没有引入新的疑问？
  - 我是否能在不进一步提问的情况下，准确、完整地执行本Skill？

只有在自检全部通过后，才能向开发者声明「已理解全貌，准备开始执行」，并在获得开发者确认后进入下一阶段。

#### 第五阶段：进入执行

多轮确认循环结束后，向开发者输出以下声明：

```
我已完整阅读并理解：
- 本Skill的全部要求与约束
- 项目上下文中的相关约定
- 相关契约中的业务规则与技术方案
- 相关实际代码的实现方式

结合你的全部回答，我确认当前不存在任何尚未澄清的不确定点。
我已准备好开始执行，过程中如遇新的未预见问题，将及时反馈。
```

开发者在聊天框回复确认后，方可正式开始本Skill规定的实质性工作。

---

**核心原则**：

- **不要不好意思问**：多一轮确认远胜于事后返工。
- **不要自行假设**：任何不确定的内容，哪怕「应该就是这样」，也必须确认。
- **不要急于执行**：进入多轮确认循环前开始任何编写或修改，均视为违规。
- **不要止于首轮**：第二轮、第三轮提问同样重要，甚至更重要。

## 三、需求整理

### 3.1 读取已确认需求

读取已确认的需求内容，整理为结构化输入：

- 需求背景与业务目标。
- 核心功能及操作场景。
- 用户角色及权限关系。
- 业务规则及约束条件。
- 边界条件及异常场景。
- 与现有业务的关联关系。

### 3.2 需求分类整理

将已确认的需求按以下维度进行结构化归类：

- 已确认需求：开发者明确提出或确认的内容。
- 待补充需求：在整理过程中发现尚未明确但影响契约编写的内容（如有）。
- 不在本次范围内的内容：明确排除的需求。

未经确认的内容不得直接写入正式产品契约。如在整理过程中发现遗漏或不明确之处，可向开发者补充提问。

## 四、产品契约编写

产品契约分为最小必要集和可选扩展集，提供的是维度参考而非封闭清单。AI应根据需求实际上下文进行推理判断，避免机械套用。

### 4.0 章节结构推断

在编写具体内容前，先分析需求特征并确定章节结构：

1. **需求特征提取**：从已确认的需求中提取关键特征标签（如涉及权限控制、复杂交互、数据精度要求、性能敏感、多端适配、未来迭代规划等）。
2. **最小必要集保底**：以下核心维度必须全部覆盖——需求背景、业务目标、业务规则、业务流程、需求范围、边界条件、验收标准。
3. **可选扩展集筛选**：根据特征标签正向选取相关扩展维度（用户角色与权限、原型图与交互说明、数据要求、性能要求、兼容性要求、后续展望），反向排除明显无关的维度。
4. **缺口识别**：检查需求的每个重要方面是否都有章节承载，如发现「无章节可归」的重要内容，必须主动新增章节并说明理由。
5. **精简校验**：确认无冗余章节，确保契约厚度与需求复杂度匹配。

输出计划编写的章节清单（格式：「章节名 → 选取理由」），确认后开始正式编写。

优先完成最小必要集，根据本次需求的实际情况决定是否增加扩展内容。

### 4.1 最小必要集

以下内容必须根据需求实际情况进行整理：

#### 1. 需求背景

说明需求产生的原因、现状及需要解决的问题。

#### 2. 业务目标

明确本次需求希望实现的业务目标及预期效果。

#### 3. 业务规则

明确业务处理规则、约束条件、判断逻辑及数据变化规则。

#### 4. 业务流程

描述完整业务流程，至少考虑正常流程、异常流程及关键边界场景。

涉及不同用户角色时，应明确各角色的操作及业务差异。

#### 5. 需求范围

明确本次需求包含的功能，以及明确不在本次需求范围内的内容。

#### 6. 边界条件

明确特殊输入、异常状态、极端情况及其他可能影响业务正确性的条件。

#### 7. 验收标准

为每项核心需求提供明确、可验证的验收标准。

避免使用正常、合理、友好等无法客观判断的描述，应明确具体操作、预期结果及判断条件。

### 4.2 可选扩展集

根据需求复杂度和实际需要选择性补充：

1. 用户角色与权限：不同角色的功能权限及数据访问范围。
2. 原型图与交互说明：页面结构、操作方式及交互要求。
3. 数据要求：业务数据的来源、内容、约束及变化要求。
4. 性能要求：业务操作的响应时间、处理能力等指标。
5. 兼容性要求：需要支持的终端、客户端或历史数据兼容要求。
6. 后续展望：本次不实施但需要考虑的后续业务方向。

不需要的扩展内容不必强行编写。

## 五、文档管理

### 5.1 固定目录

产品契约统一存放在项目根目录下：

```text
交付契约/
└── 需求名称/
    └── v1/
        └── 1.产品契约.md
```

其中：

- 需求名称应能够清晰表达本次需求。
- 首次编写使用v1。
- 后续需求迭代使用v2、v3等新版本。
- 历史版本必须保留，不得直接覆盖。

### 5.2 新需求与需求迭代

新需求：

1. 根据开发者提供的信息确定需求名称。
2. 创建对应需求目录。
3. 创建v1目录。
4. 在其中生成1.产品契约.md。

需求迭代：

1. 根据开发者指定的位置读取历史产品契约。
2. 理解原有业务规则、功能范围及验收标准。
3. 分析本次变更涉及的内容。
4. 明确新增、修改、删除及保持不变的需求。
5. 创建新的版本目录。
6. 生成完整的新版本产品契约。

新版本必须包含完整的当前有效需求，不能只记录本次变更内容。

## 六、审核与迭代

### 6.1 AI自检

检查契约是否存在以下问题：

- 信息遗漏或描述错误。
- 未经确认的推测性内容。
- 与已确认需求不一致的内容。
- 需求范围不明确或边界模糊。
- 验收标准不明确或无法验证。
- 重复、模糊或无法执行的约定。

### 6.2 开发者审核

向开发者展示产品契约初稿及待确认事项，收集修改意见。

根据反馈修改对应内容，不得只修改局部内容而忽略对其他章节的影响。

### 6.3 迭代闭环

修改完成后重新提交给开发者审核，持续循环执行上述流程，直至开发者对产品契约满意并确认通过。

## 七、执行约束

1. 必须基于已确认的需求进行契约编写，不得擅自补充或修改业务规则。
2. 产品契约只描述业务层面（「做什么」），不涉及技术实现方案（「怎么做」）。
3. 未经确认的内容不得直接写入正式产品契约。
4. 必须优先采用最小必要集，可选扩展集按需补充。
5. 不得将AI推测或建议直接写成已确认的业务规则。
6. 契约编写过程中如发现遗漏，可向开发者补充提问，但不再进行系统性的完整性分析。
7. 不得擅自修改历史版本契约。
8. 不得遗漏需求变更对原有业务流程及验收标准的影响。
9. 每项核心需求都必须具备可验证的验收标准。
10. 未经开发者最终确认，不得宣称产品契约已经定稿。

## 八、完成标准

同时满足以下条件，才算完成：

- [ ] 已读取并整理已确认的需求内容。
- [ ] 已按产品契约结构完成编写。
- [ ] 已完成AI自检。
- [ ] 已提交给开发者审核。
- [ ] 开发者已确认对产品契约满意。
- [ ] 产品契约已存放在固定目录。

完成后，向开发者说明产品契约的存放位置、版本号及本次需求的核心业务范围。
