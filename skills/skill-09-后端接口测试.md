# 后端接口自动化测试

## 一、任务目标

根据本次需求的后端测试契约、产品契约、后端技术契约、项目上下文及实际后端代码，编写并执行接口自动化测试。

验证后端接口、核心业务逻辑及数据处理是否符合契约要求，分析测试失败原因，确保测试结果准确、可追溯。

## 二、执行前提

必须读取以下文件：

1. 项目根目录下的「项目上下文.md」
2. 本次需求的1.产品契约.md
3. 本次需求的2.后端技术契约.md
4. 本次需求的3.后端测试契约.md

同时阅读本次需求涉及的实际后端代码。

本次需求的三份契约必须已经通过独立审查，并由开发者确认通过。

如果缺少必要文件、契约尚未定稿或存在影响测试执行的待确认事项，必须停止相关测试并向开发者反馈。

### 前置分析反问

开始本Skill的任何实质性工作之前，AI必须先进入一个独立的前置分析阶段。目标是穷尽一切不确定点，确保对任务全貌的理解与开发者预期完全一致。未确认无任何模糊、遗漏或歧义前，不得开始任何输出、编写或修改工作。

#### 第一阶段：全量资料研读

必须完成以下阅读任务：

1. **完整阅读本Skill全文**：逐节理解任务目标、执行步骤、输出格式、约束条件和完成标准。
2. **读取项目上下文**：读取「项目上下文.md」，理解项目架构、技术栈、编码规范及关键约束。
3. **读取相关契约**：读取本Skill要求的所有相关契约（产品契约、技术契约、测试契约等）。
4. **读取实际代码**：阅读与本次任务相关的实际代码，理解现有实现、数据结构、接口定义及调用链路。

阅读过程中建立完整的任务认知图谱：起点（当前状态）、终点（完成标准）、约束、不可为事项。

#### 第二阶段：不确定点穷尽识别

基于全面理解，AI必须主动、自主地识别所有不确定点。结合本次任务的具体业务场景、技术上下文和已有资料，自由地、发散性地思考：还有什么是我不能完全确定的？

思考方向可参考但不限于：文件是否能读到、术语是否理解、资料之间是否一致、技术方案是否可行、操作环境是否具备、输出格式是否明确、需求边界是否清晰、异常情况如何处理、开发者的真实意图是什么。任何让AI产生「应该是这样」而非「确定就是这样」的念头，都是不确定点。

**判定标准**：不是「这会不会影响执行」，而是「我能不能100%确定这件事就是这样」。只要有一丝疑问、一点猜测、一种可能的理解偏差，就必须标记为不确定点。

#### 第三阶段：首轮提问

将识别出的所有不确定点，整理为具体问题向开发者提出：

1. **分主题归类呈现**，方便逐类确认。
2. **问题必须具体**，指向具体内容（如「产品契约第3.2节某规则」、「xx.go文件中xx函数」），不得笼统。
3. **说明提问原因**，简要解释为何会影响任务正确执行。
4. **穷尽式提问**，不设上限，遗漏的代价远大于多问一句。

**禁止**：不得以「信息够了」为由跳过提问；不得将不确定点自行猜测后作为假设继续；不得自行判定某些问题「不重要」而忽略。

#### 第四阶段：多轮确认循环

开发者回答后，必须进入多轮确认循环，而非直接执行。

**每轮循环**：

1. **重读全部资料**：结合回答重新阅读本Skill、项目上下文、相关契约及实际代码。
2. **新不确定点识别**：回答是否引入新信息或新矛盾？之前未意识到的问题是否变明显了？回答中是否有需要进一步澄清的内容？
3. **补充提问**：如有新不确定点，继续提问。这是正常行为，不是上一轮工作的失败。
4. **等待回答后重复步骤1～3**。

**循环终止条件**（必须同时满足）：

- 通读全部资料后，不再发现任何不确定点。
- 对任务的目标、范围、约束、输入、输出、标准均有清晰且无歧义的理解。
- 能够明确回答以下自检问题：
  - 本Skill要求我做什么？做到什么程度算完成？
  - 项目上下文、契约和代码之间是否存在我理解不了的冲突？
  - 开发者是否已回答我所有不确定点，且答案没有引入新的疑问？
  - 我是否能在不进一步提问的情况下，准确、完整地执行本Skill？

只有在自检全部通过后，才能向开发者声明「已理解全貌，准备开始执行」，并在获得开发者确认后进入下一阶段。

#### 第五阶段：进入执行

多轮确认循环结束后，向开发者输出以下声明：

```
我已完整阅读并理解：
- 本Skill的全部要求与约束
- 项目上下文中的相关约定
- 相关契约中的业务规则与技术方案
- 相关实际代码的实现方式

结合你的全部回答，我确认当前不存在任何尚未澄清的不确定点。
我已准备好开始执行，过程中如遇新的未预见问题，将及时反馈。
```

开发者在聊天框回复确认后，方可正式开始本Skill规定的实质性工作。

---

**核心原则**：

- **不要不好意思问**：多一轮确认远胜于事后返工。
- **不要自行假设**：任何不确定的内容，哪怕「应该就是这样」，也必须确认。
- **不要急于执行**：进入多轮确认循环前开始任何编写或修改，均视为违规。
- **不要止于首轮**：第二轮、第三轮提问同样重要，甚至更重要。

## 三、测试分析

### 3.1 理解测试契约

阅读三份需求契约，明确：

- 本次需求的业务规则及验收标准。
- 后端接口及核心业务逻辑。
- 测试范围及测试策略。
- 测试用例及预期结果。
- 测试数据及数据库验证要求。
- 特殊场景及技术约束。

### 3.2 分析实际代码

结合项目现有代码，识别：

- 接口路由及请求处理方式。
- 请求参数及响应结构。
- 核心业务逻辑及调用链路。
- 身份认证及权限控制。
- 数据库访问及事务处理。
- 现有测试框架及公共测试组件。

测试实现必须符合实际代码结构，优先复用项目已有测试工具和组件，不得擅自引入新的测试依赖。

### 3.3 建立测试对应关系

测试用例必须与后端测试契约逐项对应，并能够追溯到具体契约用例。

重点覆盖：

- 正常业务流程。
- 异常业务流程。
- 边界条件。
- 请求参数校验。
- 身份认证及权限校验。
- 数据库读写及持久化验证。
- 幂等性及并发场景（业务需要时）。

不得擅自缩减测试契约规定的测试范围。

## 四、自动化测试开发

### 4.1 测试代码编写

根据后端测试契约编写自动化测试代码：

1. 优先使用项目现有测试框架。
2. 按照测试契约组织测试用例。
3. 为每个测试用例明确测试输入和操作步骤。
4. 验证接口响应及业务处理结果。
5. 验证必要的数据库数据变化。
6. 验证异常场景及边界条件。
7. 确保测试结果能够客观判断是否通过。

测试代码必须符合项目编码规范，并保持结构清晰、职责明确。

### 4.2 测试代码管理

允许AI直接新增、修改和删除测试代码。

执行时遵循以下要求：

- 测试代码变更必须属于本次需求范围。
- 优先复用现有测试组件。
- 不得擅自修改无关测试代码。
- 删除已有测试代码前必须获得开发者确认。
- 不得通过修改测试预期结果的方式掩盖业务缺陷。
- 不得擅自改变后端测试契约规定的测试要求。

### 4.3 数据库访问与测试数据管理

在必要时，允许AI Agent直接连接项目数据库，根据本次测试需要，对涉及的数据表执行查询及测试数据管理操作。

数据库访问权限包括：

- 查询：允许查询本次测试涉及的数据表及相关数据。
- 新增：允许创建本次测试所需的数据。
- 修改：只允许修改本次测试自行创建的数据。
- 删除：只允许删除本次测试自行创建的数据。

执行时必须遵循以下要求：

1. 数据库操作必须限定在本次需求涉及的数据表和测试范围内。
2. 允许查询测试所需的已有数据，但不得修改或删除测试开始前已经存在的数据。
3. 允许新增本次测试专用的数据，并记录新增数据的标识及归属关系。
4. 只允许修改、删除本次测试自行新增的数据，不得操作其他已有业务数据。
5. 不得因测试数据与已有数据存在关联，就擅自修改或删除已有数据。
6. 测试结束后，应清理本次测试自行新增且不再需要的数据。
7. 如果无法确认某条数据是否由本次测试创建，不得修改或删除，应向开发者反馈。
8. 数据库连接信息及访问权限必须来自开发者提供的合法配置，不得自行猜测或获取。
9. 不得擅自修改数据库表结构、字段、索引、约束或执行其他数据库结构变更。
10. 不得访问或修改与本次测试无关的数据表。

数据库数据级操作由AI在上述授权范围内自主执行，不需要每次操作都向开发者确认。

### 4.4 外部依赖准备

如果测试依赖的数据库表、外部服务或其他资源尚未准备好，应向开发者说明：

- 缺少的外部资源。
- 具体依赖内容。
- 需要开发者执行的准备操作。
- 相关操作说明或必要的SQL语句。

涉及创建数据表、修改表结构、创建索引及其他外部资源变更时，必须由开发者执行，AI不得擅自操作。

## 五、测试执行

### 5.1 执行自动化测试

允许AI直接执行接口自动化测试，包括：

- 执行必要的测试命令。
- 启动测试所需的依赖。
- 执行指定测试用例。
- 执行完整测试集。
- 读取和分析测试结果。

测试执行必须以实际运行结果为依据，不得根据代码推测测试通过。

### 5.2 测试失败分析

测试失败时，必须分析失败原因，并区分以下情况：

1. 业务代码缺陷：后端实现不符合契约要求。
2. 测试代码缺陷：测试逻辑、断言或执行方式存在问题。
3. 测试数据问题：测试数据不满足用例前置条件或数据状态不正确。
4. 外部依赖问题：数据库或其他依赖资源不可用、配置不正确。
5. 契约不一致：测试契约与实际技术设计或业务要求存在冲突。

不得将所有测试失败简单归类为业务代码问题。

### 5.3 失败处理

根据失败原因采取不同处理方式：

- 测试代码缺陷：允许AI直接修复测试代码。
- 测试数据问题：允许AI在本次测试数据操作权限范围内修复。
- 外部依赖问题：向开发者说明原因及处理要求。
- 业务代码缺陷：分析具体问题并提供修复建议，不得直接修改后端业务代码。
- 契约问题：暂停受影响的测试，向开发者反馈，确认后再继续。

### 5.4 重新执行测试

修复测试代码或测试数据后，必须重新执行相关测试。

必要时重新执行完整测试集，确认修改没有引入新的测试问题。

不得仅根据修改结果宣称测试通过，必须以实际执行结果为准。

## 六、测试结果报告

测试完成后，通过聊天框向开发者输出完整测试报告，不要求额外生成独立报告文件。

### 6.1 测试概况

说明：

- 本次测试范围。
- 测试用例总数。
- 测试通过数量。
- 测试失败数量。
- 未执行数量。
- 最终测试结论。

### 6.2 测试结果明细

说明各测试用例的执行结果，明确哪些通过、哪些失败、哪些未执行。

### 6.3 失败问题分析

每个失败问题必须提供：

- 对应的契约用例。
- 测试文件及测试函数。
- 接口路径。
- 实际错误信息。
- 失败原因及分析结论。
- 相关代码位置。
- 建议处理方式。

不得只提供笼统的失败描述，必须提供开发者能够定位问题的信息。

### 6.4 遗留问题

列出尚未解决的问题，包括业务代码缺陷、测试契约问题、外部依赖问题及未完成的测试项。

### 6.5 最终测试结论

根据实际执行结果明确说明：

- 测试是否全部通过。
- 是否存在未解决的失败用例。
- 是否存在未执行的测试项。
- 是否满足本次测试契约要求。

## 七、执行约束

1. 必须以已确认的三份需求契约作为测试依据。
2. 必须结合实际后端代码编写测试。
3. 必须逐项对应后端测试契约中的测试用例。
4. 不得擅自缩减测试范围或改变预期结果。
5. 不得擅自引入新的测试依赖。
6. 不得擅自修改后端业务代码。
7. 删除已有测试代码前必须获得开发者确认。
8. 不得修改或删除本次测试开始前已经存在的数据库数据。
9. 只允许新增、修改和删除本次测试自行创建的数据。
10. 不得擅自执行数据库结构变更或其他外部资源变更。
11. 测试失败必须分析具体原因，不得掩盖或忽略。
12. 所有测试结论必须以实际执行结果为依据。
13. 测试报告必须通过聊天框反馈给开发者。

- [ ] 已分析本次需求涉及的实际后端代码。
- [ ] 已明确测试范围及测试用例对应关系。
- [ ] 已完成自动化测试代码编写。
- [ ] 测试用例与后端测试契约逐项对应。
- [ ] 已完成测试数据准备及必要的数据验证。
- [ ] 已按需执行数据库查询及测试数据管理。
- [ ] 未修改或删除本次测试开始前已经存在的数据库数据。
- [ ] 已执行自动化测试并获取实际结果。
- [ ] 所有失败用例均已完成原因分析。
- [ ] 测试代码问题已修复并重新执行。
- [ ] 业务代码缺陷及契约问题已明确反馈。
- [ ] 未擅自修改后端业务代码或执行未经授权的外部操作。
- [ ] 已通过聊天框输出完整测试报告。
- [ ] 所有测试项均已执行，或未执行原因已明确说明。

完成上述工作后，即可结束本次测试任务，不要求开发者额外审核确认。
