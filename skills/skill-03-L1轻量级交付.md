# L1轻量级交付

## 一、任务目标

针对L1级简单需求，将产品需求、技术设计和验证要点合并为一份轻量级交付契约，定稿后直接开展代码开发、自我审查及功能验证，最终交付可运行的代码。

跳过前后端独立交付和独立审查环节，由同一AI Agent在同一对话窗口中完成全部工作。

## 二、执行前提

当前工作环境必须是具备本地项目文件读取、目录遍历和文件修改能力的AI Agent。

执行前检查：

1. 确认当前工作目录为项目根目录。
2. 开发者已提供完整的需求描述（含原型图等资料）。
3. 已充分沟通并确认需求细节，不存在未解决的歧义。

如果缺少必要信息或存在待确认事项，必须停止并向开发者说明。

### 前置分析反问

开始本Skill的任何实质性工作之前，AI必须先进入一个独立的前置分析阶段。目标是穷尽一切不确定点，确保对任务全貌的理解与开发者预期完全一致。未确认无任何模糊、遗漏或歧义前，不得开始任何输出、编写或修改工作。

#### 第一阶段：全量资料研读

必须完成以下阅读任务：

1. **完整阅读本Skill全文**：逐节理解任务目标、执行步骤、输出格式、约束条件和完成标准。
2. **读取项目上下文**：读取「项目上下文.md」，理解项目架构、技术栈、编码规范及关键约束。
3. **读取相关契约**：读取本Skill要求的所有相关契约（产品契约、技术契约、测试契约等）。
4. **读取实际代码**：阅读与本次任务相关的实际代码，理解现有实现、数据结构、接口定义及调用链路。

阅读过程中建立完整的任务认知图谱：起点（当前状态）、终点（完成标准）、约束、不可为事项。

#### 第二阶段：不确定点穷尽识别

基于全面理解，AI必须主动、自主地识别所有不确定点。结合本次任务的具体业务场景、技术上下文和已有资料，自由地、发散性地思考：还有什么是我不能完全确定的？

思考方向可参考但不限于：文件是否能读到、术语是否理解、资料之间是否一致、技术方案是否可行、操作环境是否具备、输出格式是否明确、需求边界是否清晰、异常情况如何处理、开发者的真实意图是什么。任何让AI产生「应该是这样」而非「确定就是这样」的念头，都是不确定点。

**判定标准**：不是「这会不会影响执行」，而是「我能不能100%确定这件事就是这样」。只要有一丝疑问、一点猜测、一种可能的理解偏差，就必须标记为不确定点。

#### 第三阶段：首轮提问

将识别出的所有不确定点，整理为具体问题向开发者提出：

1. **分主题归类呈现**，方便逐类确认。
2. **问题必须具体**，指向具体内容（如「产品契约第3.2节某规则」、「xx.go文件中xx函数」），不得笼统。
3. **说明提问原因**，简要解释为何会影响任务正确执行。
4. **穷尽式提问**，不设上限，遗漏的代价远大于多问一句。

**禁止**：不得以「信息够了」为由跳过提问；不得将不确定点自行猜测后作为假设继续；不得自行判定某些问题「不重要」而忽略。

#### 第四阶段：多轮确认循环

开发者回答后，必须进入多轮确认循环，而非直接执行。

**每轮循环**：

1. **重读全部资料**：结合回答重新阅读本Skill、项目上下文、相关契约及实际代码。
2. **新不确定点识别**：回答是否引入新信息或新矛盾？之前未意识到的问题是否变明显了？回答中是否有需要进一步澄清的内容？
3. **补充提问**：如有新不确定点，继续提问。这是正常行为，不是上一轮工作的失败。
4. **等待回答后重复步骤1～3**。

**循环终止条件**（必须同时满足）：

- 通读全部资料后，不再发现任何不确定点。
- 对任务的目标、范围、约束、输入、输出、标准均有清晰且无歧义的理解。
- 能够明确回答以下自检问题：
  - 本Skill要求我做什么？做到什么程度算完成？
  - 项目上下文、契约和代码之间是否存在我理解不了的冲突？
  - 开发者是否已回答我所有不确定点，且答案没有引入新的疑问？
  - 我是否能在不进一步提问的情况下，准确、完整地执行本Skill？

只有在自检全部通过后，才能向开发者声明「已理解全貌，准备开始执行」，并在获得开发者确认后进入下一阶段。

#### 第五阶段：进入执行

多轮确认循环结束后，向开发者输出以下声明：

```
我已完整阅读并理解：
- 本Skill的全部要求与约束
- 项目上下文中的相关约定
- 相关契约中的业务规则与技术方案
- 相关实际代码的实现方式

结合你的全部回答，我确认当前不存在任何尚未澄清的不确定点。
我已准备好开始执行，过程中如遇新的未预见问题，将及时反馈。
```

开发者在聊天框回复确认后，方可正式开始本Skill规定的实质性工作。

---

**核心原则**：

- **不要不好意思问**：多一轮确认远胜于事后返工。
- **不要自行假设**：任何不确定的内容，哪怕「应该就是这样」，也必须确认。
- **不要急于执行**：进入多轮确认循环前开始任何编写或修改，均视为违规。
- **不要止于首轮**：第二轮、第三轮提问同样重要，甚至更重要。

## 三、轻量级契约编写

### 3.1 需求理解

阅读开发者提供的需求描述，理解：

- 需求背景及业务目标。
- 核心功能及操作场景。
- 用户角色及权限关系。
- 业务规则及约束条件。
- 与现有业务的关联关系。

### 3.2 主动反问

基于需求理解，主动向开发者提问：

- 需求描述中不明确或存在歧义的地方。
- 边界条件、异常场景及极端情况。
- 与现有业务可能存在的冲突或影响。

提问应聚焦业务层面，不涉及技术实现方案。

### 3.3 简化技术设计

在编码前输出简化的技术设计思路，包括：

- 涉及的模块、页面或接口。
- 数据变更（如有）。
- 关键实现逻辑。

供开发者快速确认。技术设计确认后，方可进入契约编写。

### 3.4 契约内容

轻量级交付契约合并产品需求、技术设计和验证要点，统一存放在项目根目录下的交付契约目录中：

```text
交付契约/
└── <需求名称>/
    └── v1/
        └── 1.轻量级契约.md
```

应包含：

**需求摘要**

- 需求背景与目标。
- 核心功能及操作场景。
- 用户角色及权限。

**业务规则**

- 关键业务规则及约束。
- 边界条件及异常处理。

**技术方案**

- 涉及的模块、页面、接口。
- 数据模型变更（如有）。
- 关键实现逻辑。

**验证要点**

- 核心功能的验证方式。
- 关键业务规则的验证方式。
- 边界条件的验证方式。

**需求范围**

- 明确包含的功能。
- 明确不包含的内容。

### 3.5 契约定稿

契约编写完成后，提交给开发者审核。开发者确认后，契约正式定稿，方可开始代码开发。

## 四、代码开发

### 4.1 开发约束

- 严格遵循已定稿的轻量级交付契约，不得擅自扩大需求范围。
- 遵循项目编码规范和架构约束。
- 如需调整周边代码，必须先向开发者说明影响范围并获得确认。

### 4.2 变更范围控制

- 开发范围严格限定在需求范围内。
- 不得随意修改与本次需求无关的代码。

## 五、代码审查

### 5.1 自我审查

代码开发完成后，进行自我审查，检查：

- 代码是否符合项目编码规范。
- 业务逻辑是否正确。
- 是否存在潜在的安全风险。
- 是否引入了回归风险。

### 5.2 问题报告

审查发现问题后，不直接修复，输出问题清单，包括：

- 问题描述。
- 问题位置。
- 修复建议。

由开发者决定是否需要修复及如何修复。

## 六、功能验证

开发者根据轻量级交付契约中的验证要点进行测试：

- 核心功能是否正常工作。
- 关键业务规则是否正确执行。
- 边界条件是否正确处理。

开发者测试通过即可，不需要编写自动化测试。

## 七、执行约束

1. 必须在轻量级交付契约定稿后才能开始代码开发。
2. 开发范围严格限定在需求范围内，不得擅自扩大。
3. 如需调整周边代码，必须先获得开发者确认。
4. 代码审查发现问题后，不直接修复，输出问题清单由开发者决定。
5. 不进行独立审查，由开发者审核契约和验收代码。
6. 不需要编写自动化测试，以开发者功能验证为准。
7. 输出结果包含定稿的轻量级交付契约和可运行的代码。

## 八、完成标准

同时满足以下条件，才算完成：

- [ ] 已完成轻量级交付契约编写并定稿。
- [ ] 已按照契约完成代码开发。
- [ ] 已完成自我代码审查。
- [ ] 已向开发者输出审查问题清单（如有）。
- [ ] 开发者已完成功能验证并测试通过。
- [ ] 开发者已确认最终交付结果。

完成后，向开发者说明交付摘要及代码变更位置。
