# 前端页面自动化测试

## 一、任务目标

根据本次需求的前端测试契约、产品契约、前端技术契约、后端接口文档、项目上下文及实际前端代码，执行前端页面自动化测试。

验证页面交互、数据展示及操作后的数据变化是否符合契约要求，分析测试失败原因，确保测试结果准确、可追溯。

## 二、执行前提

必须读取以下文件：

1. 项目根目录下的「项目上下文.md」
2. 本次需求的1.产品契约.md
3. 本次需求的2.前端技术契约.md
4. 本次需求的3.前端测试契约.md

同时获取后端接口文档（如 Swagger），并阅读本次需求涉及的实际前端代码。

前端代码开发必须已完成，且前端项目已部署至可正常访问的测试环境。

本次需求的三份契约必须已经通过独立审查，并由开发者确认通过。

如果缺少必要文件、契约尚未定稿、前端项目未部署或存在影响测试执行的待确认事项，必须停止相关测试并向开发者反馈。

### 前置分析反问

开始本Skill的任何实质性工作之前，AI必须先进入一个独立的前置分析阶段。目标是穷尽一切不确定点，确保对任务全貌的理解与开发者预期完全一致。未确认无任何模糊、遗漏或歧义前，不得开始任何输出、编写或修改工作。

#### 第一阶段：全量资料研读

必须完成以下阅读任务：

1. **完整阅读本Skill全文**：逐节理解任务目标、执行步骤、输出格式、约束条件和完成标准。
2. **读取项目上下文**：读取「项目上下文.md」，理解项目架构、技术栈、编码规范及关键约束。
3. **读取相关契约**：读取本Skill要求的所有相关契约（产品契约、技术契约、测试契约等）。
4. **读取实际代码**：阅读与本次任务相关的实际代码，理解现有实现、数据结构、接口定义及调用链路。

阅读过程中建立完整的任务认知图谱：起点（当前状态）、终点（完成标准）、约束、不可为事项。

#### 第二阶段：不确定点穷尽识别

基于全面理解，AI必须主动、自主地识别所有不确定点。结合本次任务的具体业务场景、技术上下文和已有资料，自由地、发散性地思考：还有什么是我不能完全确定的？

思考方向可参考但不限于：文件是否能读到、术语是否理解、资料之间是否一致、技术方案是否可行、操作环境是否具备、输出格式是否明确、需求边界是否清晰、异常情况如何处理、开发者的真实意图是什么。任何让AI产生「应该是这样」而非「确定就是这样」的念头，都是不确定点。

**判定标准**：不是「这会不会影响执行」，而是「我能不能100%确定这件事就是这样」。只要有一丝疑问、一点猜测、一种可能的理解偏差，就必须标记为不确定点。

#### 第三阶段：首轮提问

将识别出的所有不确定点，整理为具体问题向开发者提出：

1. **分主题归类呈现**，方便逐类确认。
2. **问题必须具体**，指向具体内容（如「产品契约第3.2节某规则」、「xx.go文件中xx函数」），不得笼统。
3. **说明提问原因**，简要解释为何会影响任务正确执行。
4. **穷尽式提问**，不设上限，遗漏的代价远大于多问一句。

**禁止**：不得以「信息够了」为由跳过提问；不得将不确定点自行猜测后作为假设继续；不得自行判定某些问题「不重要」而忽略。

#### 第四阶段：多轮确认循环

开发者回答后，必须进入多轮确认循环，而非直接执行。

**每轮循环**：

1. **重读全部资料**：结合回答重新阅读本Skill、项目上下文、相关契约及实际代码。
2. **新不确定点识别**：回答是否引入新信息或新矛盾？之前未意识到的问题是否变明显了？回答中是否有需要进一步澄清的内容？
3. **补充提问**：如有新不确定点，继续提问。这是正常行为，不是上一轮工作的失败。
4. **等待回答后重复步骤1～3**。

**循环终止条件**（必须同时满足）：

- 通读全部资料后，不再发现任何不确定点。
- 对任务的目标、范围、约束、输入、输出、标准均有清晰且无歧义的理解。
- 能够明确回答以下自检问题：
  - 本Skill要求我做什么？做到什么程度算完成？
  - 项目上下文、契约和代码之间是否存在我理解不了的冲突？
  - 开发者是否已回答我所有不确定点，且答案没有引入新的疑问？
  - 我是否能在不进一步提问的情况下，准确、完整地执行本Skill？

只有在自检全部通过后，才能向开发者声明「已理解全貌，准备开始执行」，并在获得开发者确认后进入下一阶段。

#### 第五阶段：进入执行

多轮确认循环结束后，向开发者输出以下声明：

```
我已完整阅读并理解：
- 本Skill的全部要求与约束
- 项目上下文中的相关约定
- 相关契约中的业务规则与技术方案
- 相关实际代码的实现方式

结合你的全部回答，我确认当前不存在任何尚未澄清的不确定点。
我已准备好开始执行，过程中如遇新的未预见问题，将及时反馈。
```

开发者在聊天框回复确认后，方可正式开始本Skill规定的实质性工作。

---

**核心原则**：

- **不要不好意思问**：多一轮确认远胜于事后返工。
- **不要自行假设**：任何不确定的内容，哪怕「应该就是这样」，也必须确认。
- **不要急于执行**：进入多轮确认循环前开始任何编写或修改，均视为违规。
- **不要止于首轮**：第二轮、第三轮提问同样重要，甚至更重要。

## 三、测试分析

### 3.1 理解测试契约

阅读三份需求契约，明确：

- 本次需求的业务规则及验收标准。
- 涉及的页面、组件及交互流程。
- 测试范围及测试策略。
- 测试用例及预期结果。
- 数据验证要求。
- 特殊场景及技术约束。

### 3.2 分析实际代码

结合项目现有代码，识别：

- 页面结构、组件职责及交互逻辑。
- 路由配置及页面跳转方式。
- 状态管理及数据流转路径。
- 接口调用封装及响应处理方式。
- 表单校验及错误处理。
- 现有测试框架及测试组织方式。

测试实现必须符合实际代码结构，优先复用项目已有测试工具和组件，不得擅自引入新的测试依赖。

### 3.3 建立测试对应关系

测试用例必须与前端测试契约逐项对应，并能够追溯到具体契约用例。

重点覆盖：

- 正常操作流程。
- 异常提示。
- 边界输入。
- 空状态及加载状态。
- 权限控制场景。
- 页面跳转及导航。
- 表单输入与校验。
- 列表操作（分页、排序、筛选）。
- 弹窗交互及操作反馈。

不得擅自缩减测试契约规定的测试范围。

## 四、自动化测试开发与执行

### 4.1 测试执行方式

允许采用以下两种方式之一执行前端页面自动化测试：

1. **直接操作浏览器**：通过浏览器自动化工具（如 Playwright MCP）直接操作浏览器，按照测试契约执行页面交互并验证实际结果，无需专门编写测试代码。
2. **编写自动化测试脚本**：根据前端测试契约编写正式的自动化测试脚本（如 Playwright 脚本），将测试代码保留在前端代码仓库中，作为后续自动化回归测试的长期资产。

具体采用哪种方式，根据项目实际情况和开发者要求确定。

### 4.2 测试脚本编写（如选择编写脚本）

如果选择编写自动化测试脚本：

1. 优先使用项目现有测试框架。
2. 按照前端测试契约组织测试用例。
3. 为每个测试用例明确操作步骤和预期结果。
4. 验证页面表现及数据展示结果。
5. 验证异常场景及边界条件。
6. 确保测试结果能够客观判断是否通过。

测试代码必须符合项目编码规范，并保持结构清晰、职责明确。

### 4.3 测试脚本管理

允许AI直接新增、修改和删除测试脚本。

执行时遵循以下要求：

- 测试代码变更必须属于本次需求范围。
- 优先复用现有测试组件。
- 不得擅自修改无关测试代码。
- 删除已有测试代码前必须获得开发者确认。
- 不得通过修改测试预期结果的方式掩盖业务缺陷。
- 不得擅自改变前端测试契约规定的测试要求。

引入新的测试依赖或工具必须经开发者确认。

### 4.4 测试数据管理

测试账号及权限由开发者提供，AI不得自行创建或获取账号。

基础测试数据允许AI自主准备和清理。

执行时遵循以下要求：

1. 测试数据操作必须限定在本次需求涉及的测试范围内。
2. 允许使用测试环境已有的基础数据。
3. 允许新增本次测试专用的数据。
4. 涉及修改或删除测试环境已有数据时，必须先获得开发者确认。
5. 测试结束后，应清理本次测试自行新增且不再需要的数据。
6. 如果无法确认某条数据是否由本次测试创建，不得修改或删除，应向开发者反馈。

### 4.5 外部依赖准备

后端接口原则上已就绪。如果测试依赖的后端接口或其他外部资源尚未准备好，应向开发者说明：

- 缺少的外部资源。
- 具体依赖内容。
- 需要开发者执行的准备操作。

涉及后端接口或其他外部资源变更时，必须由开发者处理，AI不得擅自操作。

## 五、测试执行

### 5.1 执行自动化测试

允许AI直接执行前端页面自动化测试，包括：

- 启动测试环境或浏览器。
- 执行指定测试用例。
- 执行完整测试集。
- 读取和分析测试结果。

测试执行必须以实际运行结果为依据，不得根据代码推测测试通过。

### 5.2 测试失败分析

测试失败时，必须分析失败原因，并区分以下情况：

1. **前端业务代码缺陷**：前端实现不符合契约要求。
2. **测试脚本缺陷**：测试逻辑、断言或执行方式存在问题（仅适用于编写测试脚本的情况）。
3. **测试数据问题**：测试数据不满足用例前置条件或数据状态不正确。
4. **后端接口问题**：后端接口返回与预期不符。
5. **契约不一致**：前端测试契约与实际技术设计或业务要求存在冲突。

不得将所有测试失败简单归类为前端业务代码问题。

### 5.3 失败处理

根据失败原因采取不同处理方式：

- **测试脚本缺陷**：允许AI直接修复测试脚本。
- **测试数据问题**：允许AI在测试数据操作权限范围内修复。
- **后端接口问题**：向开发者描述问题即可，不输出修复建议，不得直接修改后端代码。
- **前端业务代码缺陷**：分析问题并提供修复建议，不得直接修改前端业务代码。由开发者决定是否修复，如需修复，交由负责前端开发的Agent执行，修复完成后由测试Agent重新执行相关测试。
- **契约问题**：暂停受影响的测试，向开发者反馈，确认后再继续。

### 5.4 重新执行测试

修复测试脚本或测试数据后，必须重新执行相关测试。

前端业务代码修复后，必须由测试Agent重新执行相关测试。

必要时重新执行完整测试集，确认修改没有引入新的测试问题。

不得仅根据修改结果宣称测试通过，必须以实际执行结果为准。

## 六、测试结果报告

测试完成后，通过聊天框向开发者输出完整测试报告，不要求额外生成独立报告文件。

### 6.1 测试概况

说明：

- 本次测试范围。
- 测试用例总数。
- 测试通过数量。
- 测试失败数量。
- 未执行数量。
- 最终测试结论。

### 6.2 测试结果明细

说明各测试用例的执行结果，明确哪些通过、哪些失败、哪些未执行。

### 6.3 失败问题分析

每个失败问题必须提供：

- 对应的契约用例。
- 测试用例编号。
- 页面路径。
- 操作步骤。
- 实际错误信息或页面表现。
- 失败原因及分析结论。
- 建议处理方式。

不得只提供笼统的失败描述，必须提供开发者能够定位问题的信息。

### 6.4 遗留问题

列出尚未解决的问题，包括前端业务代码缺陷、测试契约问题、后端接口问题及未完成的测试项。

### 6.5 最终测试结论

根据实际执行结果明确说明：

- 测试是否全部通过。
- 是否存在未解决的失败用例。
- 是否存在未执行的测试项。
- 是否满足本次前端测试契约要求。

## 七、执行约束

1. 必须以已确认的三份需求契约作为测试依据。
2. 必须结合实际前端代码编写测试或执行测试。
3. 必须逐项对应前端测试契约中的测试用例。
4. 不得擅自缩减测试范围或改变预期结果。
5. 不得擅自引入新的测试依赖。
6. 不得直接修改前端业务代码或后端代码。
7. 删除已有测试代码前必须获得开发者确认。
8. 测试账号及权限必须由开发者提供，不得自行创建。
9. 涉及修改或删除测试环境已有数据时，必须先获得开发者确认。
10. 不得擅自执行后端接口变更或其他外部资源变更。
11. 测试失败必须分析具体原因，不得掩盖或忽略。
12. 所有测试结论必须以实际执行结果为依据。
13. 测试报告必须通过聊天框反馈给开发者。

- [ ] 已读取项目根目录下的「项目上下文.md」及三份需求契约。
- [ ] 已分析本次需求涉及的实际前端代码。
- [ ] 已明确测试范围及测试用例对应关系。
- [ ] 已完成自动化测试执行（直接操作浏览器或编写测试脚本）。
- [ ] 测试用例与前端测试契约逐项对应。
- [ ] 已完成测试数据准备及必要的清理。
- [ ] 已执行前端页面自动化测试并获取实际结果。
- [ ] 所有失败用例均已完成原因分析。
- [ ] 测试脚本问题已修复并重新执行。
- [ ] 前端业务代码缺陷及契约问题已明确反馈。
- [ ] 未擅自修改前端业务代码、后端代码或执行未经授权的外部操作。
- [ ] 已通过聊天框输出完整测试报告。
- [ ] 所有测试项均已执行，或未执行原因已明确说明。

完成上述工作后，即可结束本次测试任务，不要求开发者额外审核确认。
