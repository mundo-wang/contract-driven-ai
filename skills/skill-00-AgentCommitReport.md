# AgentCommitReport

## 一、触发范围

当Agent实际新增、修改或删除项目文件时，必须应用本Skill，包括但不限于：

- 源代码、配置文件、依赖声明。
- 数据库迁移脚本、API协议文件。
- Dockerfile、CI/CD配置及构建脚本。
- README、技术文档及其他项目文件。

仅阅读代码、分析问题、提供方案或示例，没有实际修改文件时，不触发本Skill。

## 二、修改前检查

修改任何项目文件之前，必须执行`git status --short`检查工作区。

- 如果存在已暂存、未暂存或未跟踪的变更，立即停止，不得开始修改。
- 向用户列出存在变更的文件及其状态，要求用户自行处理。
- 工作区干净后，记录当前分支、HEAD提交哈希及工作区基线，作为本次任务的变更追踪依据。

禁止擅自执行`git stash`、`git reset`、`git checkout`、`git restore`、`git clean`等可能影响现有文件状态的操作，不得通过其他方式绕过工作区检查。

## 三、代码修改与检查

Agent可以自主完成用户授权范围内的文件修改，并执行必要的代码格式化、静态检查和编译检查。

允许执行：
- 代码格式化，如`gofmt`。
- 静态检查，如`go vet`、`golangci-lint run`。
- 编译检查，如`go build`。

禁止执行：
- 任何自动化测试，包括但不限于`go test`、`pytest`、`npm test`及其他等效命令。
- 通过脚本、构建工具或其他间接方式触发自动化测试。

测试由开发者负责，Agent只提供针对本次修改的测试建议，不主动执行测试。

检查结果必须如实记录，区分已通过、已失败、未执行和无法执行，不得虚构检查结果。

## 四、变更报告

每次完成项目文件修改后，必须在对话中输出结构化变更报告，然后才能询问用户是否提交。

报告必须基于实际文件差异生成，完整列出本次任务新增、修改和删除的文件，不得遗漏或虚构。

报告必须包含以下内容：

1. 变更摘要：用1～3句话概括修改目的和核心改动。
2. 变更文件列表：列出文件路径、变更类型及具体修改内容。
3. 关键实现与设计决策：说明核心业务逻辑、技术方案及重要设计选择。
4. 影响分析：说明对现有功能、API、数据库、配置、数据流及兼容性的影响。
5. 潜在风险与边界情况：说明异常场景、兼容性、并发、性能及其他潜在风险；没有明显风险时如实说明。
6. 检查结果：列出实际执行的检查命令及结果，明确标记未执行或执行失败的项目。
7. 测试建议：针对本次修改提供具体的单元测试、集成测试、接口验证及手动验证建议，适用时列出。
8. 回滚方案：涉及关键业务路径、数据库迁移、配置变更或破坏性修改时，提供具体回滚步骤及注意事项；普通修改可简要说明。

报告应详细但避免重复描述，重点说明实际修改内容、设计原因和影响范围。

输出报告前，应检查`git status --short`、`git diff --stat`和`git diff`，并额外检查新增文件的实际内容，确保报告与实际修改一致。

## 五、Git提交授权

### 5.1 授权规则

报告输出完成后，必须明确询问用户：「是否确认提交？」

未经用户明确肯定答复，禁止执行`git add`和`git commit`。

「确认」「同意提交」「可以提交」等具有明确提交意图的表达视为授权；含义模糊、仅认可修改或没有回复均不构成授权。

### 5.2 提交范围

用户确认后，必须重新检查Git状态、当前分支和HEAD，确认变更仍然属于本次任务。

- 只允许提交本次任务产生的文件变更。
- 禁止使用`git add .`、`git add -A`等无差别暂存方式。
- 必须检查暂存区，确保没有无关修改。
- 对于混合了本次任务与其他修改的文件，必须能够可靠地区分并仅暂存本次任务的差异；无法安全区分时，停止提交并询问用户。
- 如果发现其他意外变更、分支变化或HEAD变化，停止提交并说明原因，不得擅自处理。

### 5.3 提交信息

提交信息统一遵循Conventional Commits规范：

`<type>(<scope>): <description>`

根据实际修改选择`feat`、`fix`、`refactor`、`perf`、`docs`、`test`、`chore`、`build`、`ci`、`style`等类型。

提交信息应简洁、准确，体现实际修改内容，不得使用含糊描述。

提交成功后，向用户反馈提交哈希、提交信息、实际提交文件及当前工作区状态。提交失败时，如实说明原因，不得盲目重复提交。

## 六、Git安全约束

1. Agent永远禁止执行`git push`，包括普通推送、强制推送及任何间接触发推送的操作。远程推送始终由开发者手动完成。
2. 用户确认提交仅代表授权本次本地`git add`和`git commit`，不代表授权其他Git操作。
3. 未经用户明确授权，不得执行分支切换、合并、变基、历史修改、远程配置修改等操作。
4. 不得擅自覆盖、删除、清理或丢弃开发者已有的数据和文件修改。

## 七、执行流程

必须遵循以下顺序：

1. 检查Git工作区，确认干净后记录基线。
2. 执行项目文件修改。
3. 执行允许的格式化、静态检查和编译检查，不执行自动化测试。
4. 检查实际文件差异，输出完整变更报告。
5. 询问用户是否确认提交。
6. 用户明确确认后，重新检查Git状态和提交范围。
7. 仅暂存本次任务的修改，检查暂存区后执行本地提交。
8. 反馈提交结果，结束任务。

任何环节发现异常或无法确认操作安全性时，必须停止相关操作并向用户说明，不得擅自绕过约束。
