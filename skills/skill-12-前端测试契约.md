# 前端测试契约编写

## 一、任务目标

根据本次需求的产品契约、前端技术契约、后端接口文档、项目上下文及现有前端代码，制定完整的前端测试方案。

明确测试范围、测试策略、页面操作测试用例、核心场景覆盖、数据验证及测试环境要求，确保后续能够通过实际页面操作验证前端功能和数据正确性。

前端测试契约只描述「测什么」，不描述「怎么测」。不涉及具体的测试执行工具、测试框架或浏览器自动化方案，这些由后续的前端页面自动化测试环节根据实际情况确定。

## 二、执行前提

必须读取以下文件：

1. 项目根目录下的「项目上下文.md」
2. 本次需求的1.产品契约.md
3. 本次需求的2.前端技术契约.md

同时获取后端接口文档（如 Swagger），并阅读本次需求涉及的前端现有代码。

如果产品契约或前端技术契约尚未定稿，必须停止编写，要求开发者先完成前置契约确认。

如果缺少必要文件或存在影响测试设计的待确认事项，主动向开发者提问，不得自行假设。

### 前置分析反问

开始本Skill的任何实质性工作之前，AI必须先进入一个独立的前置分析阶段。目标是穷尽一切不确定点，确保对任务全貌的理解与开发者预期完全一致。未确认无任何模糊、遗漏或歧义前，不得开始任何输出、编写或修改工作。

#### 第一阶段：全量资料研读

必须完成以下阅读任务：

1. **完整阅读本Skill全文**：逐节理解任务目标、执行步骤、输出格式、约束条件和完成标准。
2. **读取项目上下文**：读取「项目上下文.md」，理解项目架构、技术栈、编码规范及关键约束。
3. **读取相关契约**：读取本Skill要求的所有相关契约（产品契约、技术契约、测试契约等）。
4. **读取实际代码**：阅读与本次任务相关的实际代码，理解现有实现、数据结构、接口定义及调用链路。

阅读过程中建立完整的任务认知图谱：起点（当前状态）、终点（完成标准）、约束、不可为事项。

#### 第二阶段：不确定点穷尽识别

基于全面理解，AI必须主动、自主地识别所有不确定点。结合本次任务的具体业务场景、技术上下文和已有资料，自由地、发散性地思考：还有什么是我不能完全确定的？

思考方向可参考但不限于：文件是否能读到、术语是否理解、资料之间是否一致、技术方案是否可行、操作环境是否具备、输出格式是否明确、需求边界是否清晰、异常情况如何处理、开发者的真实意图是什么。任何让AI产生「应该是这样」而非「确定就是这样」的念头，都是不确定点。

**判定标准**：不是「这会不会影响执行」，而是「我能不能100%确定这件事就是这样」。只要有一丝疑问、一点猜测、一种可能的理解偏差，就必须标记为不确定点。

#### 第三阶段：首轮提问

将识别出的所有不确定点，整理为具体问题向开发者提出：

1. **分主题归类呈现**，方便逐类确认。
2. **问题必须具体**，指向具体内容（如「产品契约第3.2节某规则」、「xx.go文件中xx函数」），不得笼统。
3. **说明提问原因**，简要解释为何会影响任务正确执行。
4. **穷尽式提问**，不设上限，遗漏的代价远大于多问一句。

**禁止**：不得以「信息够了」为由跳过提问；不得将不确定点自行猜测后作为假设继续；不得自行判定某些问题「不重要」而忽略。

#### 第四阶段：多轮确认循环

开发者回答后，必须进入多轮确认循环，而非直接执行。

**每轮循环**：

1. **重读全部资料**：结合回答重新阅读本Skill、项目上下文、相关契约及实际代码。
2. **新不确定点识别**：回答是否引入新信息或新矛盾？之前未意识到的问题是否变明显了？回答中是否有需要进一步澄清的内容？
3. **补充提问**：如有新不确定点，继续提问。这是正常行为，不是上一轮工作的失败。
4. **等待回答后重复步骤1～3**。

**循环终止条件**（必须同时满足）：

- 通读全部资料后，不再发现任何不确定点。
- 对任务的目标、范围、约束、输入、输出、标准均有清晰且无歧义的理解。
- 能够明确回答以下自检问题：
  - 本Skill要求我做什么？做到什么程度算完成？
  - 项目上下文、契约和代码之间是否存在我理解不了的冲突？
  - 开发者是否已回答我所有不确定点，且答案没有引入新的疑问？
  - 我是否能在不进一步提问的情况下，准确、完整地执行本Skill？

只有在自检全部通过后，才能向开发者声明「已理解全貌，准备开始执行」，并在获得开发者确认后进入下一阶段。

#### 第五阶段：进入执行

多轮确认循环结束后，向开发者输出以下声明：

```
我已完整阅读并理解：
- 本Skill的全部要求与约束
- 项目上下文中的相关约定
- 相关契约中的业务规则与技术方案
- 相关实际代码的实现方式

结合你的全部回答，我确认当前不存在任何尚未澄清的不确定点。
我已准备好开始执行，过程中如遇新的未预见问题，将及时反馈。
```

开发者在聊天框回复确认后，方可正式开始本Skill规定的实质性工作。

---

**核心原则**：

- **不要不好意思问**：多一轮确认远胜于事后返工。
- **不要自行假设**：任何不确定的内容，哪怕「应该就是这样」，也必须确认。
- **不要急于执行**：进入多轮确认循环前开始任何编写或修改，均视为违规。
- **不要止于首轮**：第二轮、第三轮提问同样重要，甚至更重要。

## 三、测试分析

### 3.1 理解需求与技术方案

阅读产品契约和前端技术契约，明确：

- 本次需求的业务规则及验收标准。
- 涉及的页面、组件及交互流程。
- 核心用户操作场景及状态变化。
- 需要调用的后端接口及数据处理方式。
- 表单字段、校验规则及错误提示方式。
- 技术约束及异常处理方式。

### 3.2 分析现有代码

结合项目上下文，阅读本次需求涉及的前端实际代码，识别：

- 页面结构、组件职责及交互逻辑。
- 路由配置及页面跳转方式。
- 状态管理及数据流转路径。
- 接口调用封装及响应处理。
- 表单校验及错误处理。
- 权限判断及无权限展示策略。
- 现有测试代码及测试组织方式。

测试方案必须结合实际代码制定，不能仅根据契约中的文字描述编写。

### 3.3 识别测试场景

根据业务和前端技术实现，主动识别以下测试场景：

- 正常操作流程。
- 异常提示（如网络错误、接口返回错误）。
- 边界输入及极限值。
- 空状态及加载状态。
- 权限控制场景。
- 页面跳转及导航。
- 表单输入与校验。
- 列表操作（分页、排序、筛选）。
- 弹窗交互及操作反馈。

对于契约中遗漏的测试场景，允许提出补充建议，由开发者确认后纳入正式测试契约。

## 四、测试契约编写

测试契约分为最小必要集和可选扩展集，提供的是维度参考而非封闭清单。AI应根据需求实际上下文进行推理判断，避免机械套用。

### 4.0 章节结构推断

在编写具体内容前，先分析测试需求特征并确定章节结构：

1. **测试特征提取**：从产品契约、前端技术契约和代码分析中提取关键特征标签（如涉及多端兼容、响应式布局、权限控制、公共组件变更等）。
2. **最小必要集保底**：以下核心维度必须全部覆盖——测试范围、测试策略、页面操作测试用例、核心场景覆盖、数据验证、测试环境要求。
3. **可选扩展集筛选**：根据特征标签正向选取相关扩展维度（兼容性测试、响应式测试、权限测试、回归测试范围），反向排除明显无关的维度。
4. **缺口识别**：检查测试需求的每个重要方面是否都有章节承载，如发现「无章节可归」的重要内容，必须主动新增章节并说明理由。
5. **精简校验**：确认无冗余章节，确保契约厚度与需求复杂度匹配。

输出计划编写的章节清单（格式：「章节名 → 选取理由」），确认后开始正式编写。

优先完成最小必要集，根据需求实际情况补充可选扩展内容。

### 4.1 最小必要集

#### 1. 测试范围

明确本次需要测试的页面、组件、交互流程及数据验证点，说明不在本次测试范围内的内容。

#### 2. 测试策略

说明测试类型、测试优先级及测试重点。

测试契约只描述「测什么」，不描述「怎么测」。不涉及具体的测试执行工具、测试框架或浏览器自动化方案。

#### 3. 页面操作测试用例

每个测试用例必须明确：

- 用例编号。
- 测试场景。
- 前置条件。
- 操作步骤（点击、输入、跳转等）。
- 预期页面表现。
- 预期数据展示结果。

操作步骤必须具体、可复现，预期结果必须能够客观判断是否通过。

#### 4. 核心场景覆盖

明确正常操作流程、异常处理、边界条件及关键交互规则的覆盖情况。

避免只覆盖正常流程而忽略异常情况。

#### 5. 数据验证

明确需要验证的数据内容：

- 页面获取和展示的数据是否正确。
- 数据内容是否符合业务预期。
- 执行操作后数据的变化是否符合预期。
- 错误状态下的数据展示。

以后端接口返回数据为验证准据。

#### 6. 测试环境要求

说明测试所需的账号、权限、后端接口状态及测试数据准备要求。

### 4.2 可选扩展集

根据需求实际情况选择性补充：

1. 兼容性测试：明确目标浏览器及设备清单，以及需要验证的兼容性要点。
2. 响应式测试：验证不同屏幕分辨率下的页面布局、组件展示及交互表现。
3. 权限测试：验证不同用户角色下的页面元素可见性及操作权限。
4. 回归测试范围：明确本次变更可能影响的已有页面、组件及交互功能。

不涉及的内容无需强行补充。

## 五、文档管理

### 5.1 固定目录

前端测试契约与产品契约、前端技术契约放在同一个需求版本目录下：

```text
交付契约/
└── 需求名称/
    └── v1/
        ├── 1.产品契约.md
        ├── 2.前端技术契约.md
        └── 3.前端测试契约.md
```

### 5.2 版本管理

1. 新需求使用对应的v1目录。
2. 需求迭代使用开发者指定的新版本目录。
3. 历史版本必须保留，不得直接覆盖。
4. 新版本必须生成完整的前端测试契约，不能只记录本次变更内容。

## 六、审核与迭代

测试契约初稿完成后，必须经过审核。

### 6.1 AI自检

检查：

- 测试范围是否覆盖本次需求。
- 测试策略是否聚焦「测什么」。
- 核心业务场景是否覆盖完整。
- 正常、异常及边界场景是否遗漏。
- 测试用例是否具备明确的操作步骤。
- 预期结果是否可验证。
- 数据验证是否完整。
- 测试环境要求是否明确。
- 是否存在重复或无效用例。

### 6.2 开发者审核

向开发者展示测试契约初稿及待确认事项，收集修改意见。

对于AI发现但契约尚未覆盖的测试场景，说明补充原因，由开发者确认。

### 6.3 一致性检查

每次修改完成后，必须重新检查：

1. 测试范围是否符合产品契约。
2. 测试用例是否覆盖产品契约中的业务规则和验收标准。
3. 测试用例是否覆盖前端技术契约中的页面、交互及接口调用。
4. 数据验证是否符合后端接口文档中的响应结构。
5. 测试策略是否聚焦测试内容而非执行方式。
6. 是否存在与实际代码不一致的测试设计。
7. 是否存在未经确认的测试要求。

发现冲突或无法确认的内容时，主动向开发者反馈，不得自行决定。

重复执行修改、检查和审核，直到开发者确认定稿。

## 七、执行约束

1. 必须以产品契约、前端技术契约及项目上下文作为测试设计依据。
2. 每个测试用例必须能够追溯到具体业务规则、验收标准或技术设计。
3. 不得遗漏正常、异常及边界场景。
4. 不得使用无法验证的预期结果。
5. 不得将未经确认的测试建议直接写入正式契约。
6. 不得擅自修改产品契约和前端技术契约。
7. 不得擅自修改业务代码及其他非目标文档。
8. 不得覆盖历史版本测试契约。
9. 测试契约只描述「测什么」，不描述「怎么测」。
10. 未经开发者确认，不得宣称测试契约已经定稿。

## 八、完成标准

同时满足以下条件，才算完成：

- [ ] 已读取项目根目录下的「项目上下文.md」及两份前置契约。
- [ ] 已完成相关前端代码分析。
- [ ] 已明确测试范围和测试策略。
- [ ] 已完成最小必要集。
- [ ] 必要的可选扩展内容已补充。
- [ ] 核心测试用例具备明确步骤及可验证的预期结果。
- [ ] 测试用例能够追溯到产品契约的验收标准或前端技术契约的交互逻辑。
- [ ] 测试契约已存放在规定目录。
- [ ] 已完成AI自检及一致性检查。
- [ ] 开发者已审核并确认定稿。

完成后，向开发者说明测试契约的存放位置、测试覆盖范围及主要测试策略。
