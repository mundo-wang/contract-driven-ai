# 前端测试契约编写

## 一、任务目标

根据本次需求的产品契约、前端技术契约、后端接口文档、项目上下文及现有前端代码，制定完整的前端测试方案。

明确测试范围、测试策略、页面操作测试用例、核心场景覆盖、数据验证及测试环境要求，确保后续能够通过实际页面操作验证前端功能和数据正确性。

前端测试契约只描述「测什么」，不描述「怎么测」。不涉及具体的测试执行工具、测试框架或浏览器自动化方案，这些由后续的前端页面自动化测试环节根据实际情况确定。

## 二、执行前提

必须读取以下文件：

1. 项目根目录下的"项目上下文.md"
2. 本次需求的1.产品契约.md
3. 本次需求的2.前端技术契约.md

同时获取后端接口文档（如 Swagger），并阅读本次需求涉及的前端现有代码。

如果产品契约或前端技术契约尚未定稿，必须停止编写，要求开发者先完成前置契约确认。

如果缺少必要文件或存在影响测试设计的待确认事项，主动向开发者提问，不得自行假设。

### 前置分析反问

开始执行前，AI必须先完成以下步骤：

1. **资料分析**：仔细阅读本Skill要求读取的全部资料，包括项目上下文、相关契约及实际代码，全面理解本次任务的范围、目标和约束。
2. **识别不确定点**：基于资料分析，主动识别以下类型的问题：
   - 资料之间存在矛盾、冲突或不一致的地方。
   - 契约、代码或文档中存在模糊、遗漏或无法确认的内容。
   - 本Skill的流程、标准或要求与当前项目实际情况可能存在不匹配的地方。
   - 开发者可能尚未明确说明，但对本次任务执行有实质性影响的约束、例外或特殊要求。
3. **列举并提问**：将识别出的不确定点整理为具体问题，向开发者提问。提问应聚焦影响任务正确性的关键问题，避免重复询问已经明确的信息。
4. **确认后执行**：开发者解答后，AI以解答为准开展后续工作。如经分析后不存在不确定点，可直接开始执行。

## 三、测试分析

### 3.1 理解需求与技术方案

阅读产品契约和前端技术契约，明确：

- 本次需求的业务规则及验收标准。
- 涉及的页面、组件及交互流程。
- 核心用户操作场景及状态变化。
- 需要调用的后端接口及数据处理方式。
- 表单字段、校验规则及错误提示方式。
- 技术约束及异常处理方式。

### 3.2 分析现有代码

结合项目上下文，阅读本次需求涉及的前端实际代码，识别：

- 页面结构、组件职责及交互逻辑。
- 路由配置及页面跳转方式。
- 状态管理及数据流转路径。
- 接口调用封装及响应处理。
- 表单校验及错误处理。
- 权限判断及无权限展示策略。
- 现有测试代码及测试组织方式。

测试方案必须结合实际代码制定，不能仅根据契约中的文字描述编写。

### 3.3 识别测试场景

根据业务和前端技术实现，主动识别以下测试场景：

- 正常操作流程。
- 异常提示（如网络错误、接口返回错误）。
- 边界输入及极限值。
- 空状态及加载状态。
- 权限控制场景。
- 页面跳转及导航。
- 表单输入与校验。
- 列表操作（分页、排序、筛选）。
- 弹窗交互及操作反馈。

对于契约中遗漏的测试场景，允许提出补充建议，由开发者确认后纳入正式测试契约。

## 四、测试契约编写

测试契约分为最小必要集和可选扩展集。

优先完成最小必要集，根据需求实际情况补充可选扩展内容。

### 4.1 最小必要集

#### 1. 测试范围

明确本次需要测试的页面、组件、交互流程及数据验证点，说明不在本次测试范围内的内容。

#### 2. 测试策略

说明测试类型、测试优先级及测试重点。

测试契约只描述「测什么」，不描述「怎么测」。不涉及具体的测试执行工具、测试框架或浏览器自动化方案。

#### 3. 页面操作测试用例

每个测试用例必须明确：

- 用例编号。
- 测试场景。
- 前置条件。
- 操作步骤（点击、输入、跳转等）。
- 预期页面表现。
- 预期数据展示结果。

操作步骤必须具体、可复现，预期结果必须能够客观判断是否通过。

#### 4. 核心场景覆盖

明确正常操作流程、异常处理、边界条件及关键交互规则的覆盖情况。

避免只覆盖正常流程而忽略异常情况。

#### 5. 数据验证

明确需要验证的数据内容：

- 页面获取和展示的数据是否正确。
- 数据内容是否符合业务预期。
- 执行操作后数据的变化是否符合预期。
- 错误状态下的数据展示。

以后端接口返回数据为验证准据。

#### 6. 测试环境要求

说明测试所需的账号、权限、后端接口状态及测试数据准备要求。

### 4.2 可选扩展集

根据需求实际情况选择性补充：

1. 兼容性测试：明确目标浏览器及设备清单，以及需要验证的兼容性要点。
2. 响应式测试：验证不同屏幕分辨率下的页面布局、组件展示及交互表现。
3. 权限测试：验证不同用户角色下的页面元素可见性及操作权限。
4. 回归测试范围：明确本次变更可能影响的已有页面、组件及交互功能。

不涉及的内容无需强行补充。

## 五、文档管理

### 5.1 固定目录

前端测试契约与产品契约、前端技术契约放在同一个需求版本目录下：

```text
交付契约/
└── 需求名称/
    └── v1/
        ├── 1.产品契约.md
        ├── 2.前端技术契约.md
        └── 3.前端测试契约.md
```

### 5.2 版本管理

1. 新需求使用对应的v1目录。
2. 需求迭代使用开发者指定的新版本目录。
3. 历史版本必须保留，不得直接覆盖。
4. 新版本必须生成完整的前端测试契约，不能只记录本次变更内容。

## 六、审核与迭代

测试契约初稿完成后，必须经过审核。

### 6.1 AI自检

检查：

- 测试范围是否覆盖本次需求。
- 测试策略是否聚焦「测什么」。
- 核心业务场景是否覆盖完整。
- 正常、异常及边界场景是否遗漏。
- 测试用例是否具备明确的操作步骤。
- 预期结果是否可验证。
- 数据验证是否完整。
- 测试环境要求是否明确。
- 是否存在重复或无效用例。

### 6.2 开发者审核

向开发者展示测试契约初稿及待确认事项，收集修改意见。

对于AI发现但契约尚未覆盖的测试场景，说明补充原因，由开发者确认。

### 6.3 一致性检查

每次修改完成后，必须重新检查：

1. 测试范围是否符合产品契约。
2. 测试用例是否覆盖产品契约中的业务规则和验收标准。
3. 测试用例是否覆盖前端技术契约中的页面、交互及接口调用。
4. 数据验证是否符合后端接口文档中的响应结构。
5. 测试策略是否聚焦测试内容而非执行方式。
6. 是否存在与实际代码不一致的测试设计。
7. 是否存在未经确认的测试要求。

发现冲突或无法确认的内容时，主动向开发者反馈，不得自行决定。

重复执行修改、检查和审核，直到开发者确认定稿。

## 七、执行约束

1. 必须以产品契约、前端技术契约及项目上下文作为测试设计依据。
2. 每个测试用例必须能够追溯到具体业务规则、验收标准或技术设计。
3. 不得遗漏正常、异常及边界场景。
4. 不得使用无法验证的预期结果。
5. 不得将未经确认的测试建议直接写入正式契约。
6. 不得擅自修改产品契约和前端技术契约。
7. 不得擅自修改业务代码及其他非目标文档。
8. 不得覆盖历史版本测试契约。
9. 测试契约只描述「测什么」，不描述「怎么测」。
10. 未经开发者确认，不得宣称测试契约已经定稿。

## 八、完成标准

同时满足以下条件，才算完成：

- [ ] 已读取项目根目录下的"项目上下文.md"及两份前置契约。
- [ ] 已完成相关前端代码分析。
- [ ] 已明确测试范围和测试策略。
- [ ] 已完成最小必要集。
- [ ] 必要的可选扩展内容已补充。
- [ ] 核心测试用例具备明确步骤及可验证的预期结果。
- [ ] 测试用例能够追溯到产品契约的验收标准或前端技术契约的交互逻辑。
- [ ] 测试契约已存放在规定目录。
- [ ] 已完成AI自检及一致性检查。
- [ ] 开发者已审核并确认定稿。

完成后，向开发者说明测试契约的存放位置、测试覆盖范围及主要测试策略。
