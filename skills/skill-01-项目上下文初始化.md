# 项目上下文初始化

## 一、任务目标

分析当前项目，建立准确、完整的项目上下文，并在项目根目录下生成以下文档：

```text
项目上下文.md
```

本Skill负责项目分析、架构设计建议、文档生成及审核，不负责修改业务代码。

## 二、执行前提

当前工作环境必须是具备本地项目文件读取、目录遍历和文件修改能力的AI Agent。

执行前检查：

1. 确认当前工作目录为项目根目录。
2. 检查项目是否包含实际业务代码。
3. 检查「项目上下文.md」是否已经存在。
4. 如果文档已存在，先读取现有内容，不得直接覆盖。

根据业务代码情况识别项目类型：

- 新项目：已经创建项目目录，但尚无实际业务代码。
- 存量项目：已经存在实际业务代码。

### 前置分析反问

开始本Skill的任何实质性工作之前，AI必须先进入一个独立的前置分析阶段。目标是穷尽一切不确定点，确保对任务全貌的理解与开发者预期完全一致。未确认无任何模糊、遗漏或歧义前，不得开始任何输出、编写或修改工作。

#### 第一阶段：全量资料研读

必须完成以下阅读任务：

1. **完整阅读本Skill全文**：逐节理解任务目标、执行步骤、输出格式、约束条件和完成标准。
2. **读取项目上下文**：读取「项目上下文.md」，理解项目架构、技术栈、编码规范及关键约束。
3. **读取相关契约**：读取本Skill要求的所有相关契约（产品契约、技术契约、测试契约等）。
4. **读取实际代码**：阅读与本次任务相关的实际代码，理解现有实现、数据结构、接口定义及调用链路。

阅读过程中建立完整的任务认知图谱：起点（当前状态）、终点（完成标准）、约束、不可为事项。

#### 第二阶段：不确定点穷尽识别

基于全面理解，AI必须主动、自主地识别所有不确定点。结合本次任务的具体业务场景、技术上下文和已有资料，自由地、发散性地思考：还有什么是我不能完全确定的？

思考方向可参考但不限于：文件是否能读到、术语是否理解、资料之间是否一致、技术方案是否可行、操作环境是否具备、输出格式是否明确、需求边界是否清晰、异常情况如何处理、开发者的真实意图是什么。任何让AI产生「应该是这样」而非「确定就是这样」的念头，都是不确定点。

**判定标准**：不是「这会不会影响执行」，而是「我能不能100%确定这件事就是这样」。只要有一丝疑问、一点猜测、一种可能的理解偏差，就必须标记为不确定点。

#### 第三阶段：首轮提问

将识别出的所有不确定点，整理为具体问题向开发者提出：

1. **分主题归类呈现**，方便逐类确认。
2. **问题必须具体**，指向具体内容（如「产品契约第3.2节某规则」、「xx.go文件中xx函数」），不得笼统。
3. **说明提问原因**，简要解释为何会影响任务正确执行。
4. **穷尽式提问**，不设上限，遗漏的代价远大于多问一句。

**禁止**：不得以「信息够了」为由跳过提问；不得将不确定点自行猜测后作为假设继续；不得自行判定某些问题「不重要」而忽略。

#### 第四阶段：多轮确认循环

开发者回答后，必须进入多轮确认循环，而非直接执行。

**每轮循环**：

1. **重读全部资料**：结合回答重新阅读本Skill、项目上下文、相关契约及实际代码。
2. **新不确定点识别**：回答是否引入新信息或新矛盾？之前未意识到的问题是否变明显了？回答中是否有需要进一步澄清的内容？
3. **补充提问**：如有新不确定点，继续提问。这是正常行为，不是上一轮工作的失败。
4. **等待回答后重复步骤1～3**。

**循环终止条件**（必须同时满足）：

- 通读全部资料后，不再发现任何不确定点。
- 对任务的目标、范围、约束、输入、输出、标准均有清晰且无歧义的理解。
- 能够明确回答以下自检问题：
  - 本Skill要求我做什么？做到什么程度算完成？
  - 项目上下文、契约和代码之间是否存在我理解不了的冲突？
  - 开发者是否已回答我所有不确定点，且答案没有引入新的疑问？
  - 我是否能在不进一步提问的情况下，准确、完整地执行本Skill？

只有在自检全部通过后，才能向开发者声明「已理解全貌，准备开始执行」，并在获得开发者确认后进入下一阶段。

#### 第五阶段：进入执行

多轮确认循环结束后，向开发者输出以下声明：

```
我已完整阅读并理解：
- 本Skill的全部要求与约束
- 项目上下文中的相关约定
- 相关契约中的业务规则与技术方案
- 相关实际代码的实现方式

结合你的全部回答，我确认当前不存在任何尚未澄清的不确定点。
我已准备好开始执行，过程中如遇新的未预见问题，将及时反馈。
```

开发者在聊天框回复确认后，方可正式开始本Skill规定的实质性工作。

---

**核心原则**：

- **不要不好意思问**：多一轮确认远胜于事后返工。
- **不要自行假设**：任何不确定的内容，哪怕「应该就是这样」，也必须确认。
- **不要急于执行**：进入多轮确认循环前开始任何编写或修改，均视为违规。
- **不要止于首轮**：第二轮、第三轮提问同样重要，甚至更重要。

## 三、新项目初始化

### 3.1 收集项目信息

如果识别为新项目，主动告知开发者当前项目尚无业务代码，并了解：

- 项目背景与业务目标。
- 核心业务功能。
- 主要业务模块。
- 开发语言及技术栈。
- 数据库、缓存及外部依赖。
- 开发者已确定的技术约束。

根据开发者提供的信息逐步提问，不要求一次性收集全部内容。

### 3.2 提出架构建议

结合业务需求和技术约束，主动提出架构设计建议，重点关注：

- 整体架构及分层设计。
- 核心模块划分及职责。
- 模块之间的依赖关系。
- 数据库及数据模型设计。
- 接口设计规范。
- 公共组件及技术选型。

对于关键技术决策，说明推荐方案及选择依据，必要时提供备选方案。

所有架构建议必须经过开发者确认后，才能作为正式项目约定写入文档。

### 3.3 生成文档

架构方案确认后，整理项目信息并生成「项目上下文.md」。新项目尚无业务代码，动态信息索引章节可暂留空或由开发者提供预期目录结构。

## 四、存量项目初始化

如果识别为存量项目，必须优先通过实际代码分析项目，不得仅依赖开发者的口头描述。

### 4.1 项目结构分析

遍历项目目录，识别整体目录结构、核心业务模块、公共组件及各模块职责。

同步扫描以下动态信息的可能存放位置，为动态信息索引章节提供候选：
- 错误码定义文件或目录。
- 公共组件/工具包目录。
- 接口路由注册目录。
- 数据库模型/结构体定义目录。
- 配置文件或配置加载目录。
- 其他项目中可能频繁变化但具有明确存放位置的信息。

### 4.2 技术栈分析

读取依赖配置，识别开发语言、框架、ORM、数据库、缓存及其他核心依赖，尽可能确认具体版本。

### 4.3 架构分析

阅读核心业务代码，梳理：

- 整体架构及分层设计。
- 模块职责及调用关系。
- 接口定义及路由组织方式。
- 数据模型及数据库访问方式。
- 公共组件及工具封装。
- 核心业务数据流。

### 4.4 编码规范分析

结合实际代码，提取：

- 命名规范及代码风格。
- 目录和文件组织方式。
- 结构体、接口及模型定义规范。
- 错误处理规范。
- 日志及公共组件使用规范。
- 测试代码组织及编写规范。

无法从代码确认的信息必须标记为待确认，并主动向开发者提问，不得自行推测。

### 4.5 生成文档

完成代码分析后，整理已确认信息和待确认事项，生成「项目上下文.md」初稿。

## 五、文档内容要求

文档存放位置固定为项目根目录下的「项目上下文.md」，不得擅自调整路径或拆分为其他文件。具体章节允许根据项目实际情况灵活增删。

文档仅包含不易变更的静态约定，不展开描述随代码迭代可能变化的具体实现细节（如模块清单、公共组件列表、接口定义、错误码等）。这些动态信息通过动态信息索引章节指明其在代码库中的位置。

建议包含以下章节：

| 章节 | 说明 |
|------|------|
| 项目基本信息 | 项目名称、背景、目标及核心业务领域 |
| 技术栈 | 开发语言、主框架、数据库、缓存、部署方式等核心技术选型 |
| 架构原则与分层约束 | 分层模式、层间调用规则、模块粗粒度边界原则 |
| 命名规范 | 包名、文件、变量、函数、结构体、接口、常量及数据库对象的命名规则 |
| 代码风格与基础约定 | 缩进、换行、注释、导包顺序、错误处理原则、结构体标签约定、日志要求 |
| 领域术语表 | 核心业务概念及专有名词解释，避免后续沟通歧义 |
| 关键全局约束 | 认证授权方式、统一响应/错误封装格式约定、敏感信息处理原则 |
| 动态信息索引 | 以表格形式指明错误码、公共组件、路由、模型等动态信息在代码库中的位置 |

上述章节为建议内容，可根据项目实际情况动态补充其他章节，但需与开发者沟通确认。

不得为了填充章节而编造项目不存在的技术或规范。

## 六、文档审核与迭代

文档生成后，必须经过开发者审核，不得直接宣布完成。

### 6.1 AI自检

检查文档是否存在以下问题：

- 信息遗漏或描述错误。
- 未经确认的推测性内容。
- 与实际代码不一致的内容。
- 稳定约定之间是否存在内在矛盾（如命名规范与架构原则冲突）。
- 重复、模糊或无法执行的约定。
- 动态信息索引中指向的路径是否真实存在于代码库中。

### 6.2 开发者审核

向开发者展示文档内容及待确认事项，收集修改意见。

根据反馈修改对应文档，不得只修改局部内容而忽略对其他文档的影响。

### 6.3 建议补充章节（可选）

基于项目分析，AI主动识别是否需要补充默认章节之外的内容：

1. 扫描项目代码及依赖，识别项目中已使用但未在默认章节中覆盖的技术或能力（如消息队列、缓存策略、分布式事务等）。
2. 将识别出的候选补充章节通过聊天框向开发者展示，说明建议补充的理由。
3. **不得直接写入文档**，需等待开发者确认后再添加。
4. 如果开发者认为无需补充，则跳过此环节。

### 6.4 审核迭代

每次修改完成后，必须重新检查：

1. 文档中稳定约定之间是否存在内在矛盾。
2. 动态信息索引指向的路径是否仍然有效。
3. 是否存在与实际代码冲突的描述。
4. 是否存在未经确认的推测性内容。

发现问题时，分析原因并向开发者确认，不得自行判断后直接修改。

重复执行修改、检查和审核，直到开发者确认文档定稿。

## 七、执行约束

1. 项目上下文必须基于实际代码和开发者确认的信息。
2. 不得将推测或行业惯例当作项目既定规范。
3. 新项目允许主动提出架构建议，但未经确认不得写入正式约定。
4. 存量项目以实际代码为事实依据，不得擅自改变现有架构描述。
5. 未确认的信息必须主动提问，不得自行补全。
6. 不得擅自修改业务代码、配置文件或其他非目标文档。
7. 不得擅自引入新的技术栈、依赖或架构方案。
8. 不得擅自调整「项目上下文.md」的存放路径。
9. 每次修改后必须执行AI自检。
10. 如果发现文档与实际代码不一致，必须向开发者反馈，不得自行判断哪一方正确。

## 八、完成标准

同时满足以下条件，才算完成：

- [ ] 已正确识别项目类型。
- [ ] 已完成项目需求收集或存量代码分析。
- [ ] 已生成「项目上下文.md」。
- [ ] 文档存放在项目根目录。
- [ ] 未确认的信息已明确标记或完成确认。
- [ ] 文档中不存在未解决的内在矛盾。
- [ ] 动态信息索引中指向的路径均已验证真实存在（如已填写）。
- [ ] 文档内容已经开发者最终审核确认。

完成后，向开发者说明文档存放位置、核心分析结果、建议补充章节（如有）及尚未解决的待确认事项。
